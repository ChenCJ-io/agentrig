# AgentRig 定位与命名

> 最后更新：2026-07-07 · 状态：✅ 定稿

## 项目名

**AgentRig**

- `rig`：测试台、钻井装备、装备 ——「给 agent 上测试台」
- 避开阿里 [AgentScope](https://github.com/agentscope-ai/agentscope)（multi-agent 框架，命名硬冲突）
- 避开心智占有者：Langfuse / promptfoo / mcp-eval / EvalView / AgentBench（清华） / Guardrails AI

## 产品愿景：让 agent 回归用例随开发自动积累

> **Every change grows the suite. Every release runs it all.**
> （每次改动都在长用例，每次发版都跑全量。）

AgentRig 不是「测试工具」，是**开发者的 agent 回归资产管家**。核心是一个**用例积累飞轮**：

1. 开发者改业务 agent 代码
2. CC/Codex 看代码 + 读 AgentRig 历史数据，针对本次改动生成 mock + 用例
3. CC 跑相关用例，看本次改动有没有回归（**开发时 · 增量**）
4. 用例自动沉淀到用例库，越用越厚
5. 发版时跑全量积累用例做最终验证（**发版时 · 全量**）

**飞轮效应**：用得越多 → 用例库越厚 → 回归网越密 → agent 质量越高 → 开发越敢改 → 用得越多。

### 三层护城河（产品层最深）

| 层 | 内容 | 深度 |
|---|---|---|
| **产品层（真护城河）** | 用例积累飞轮 —— 用例库是迁移成本最高的资产，越用越离不开 | 深 |
| 技术层 | MCP 工具层测试（proxy + mock + 可信数据），vs Langfuse 对话层观测 | 中（竞品可追）|
| 入口层 | 编码 Agent 通过 MCP 驱动 + **开箱即用的 CC 测试 skill 包**（见 `08`） | 中（方法论沉淀，竞品没有）|

Langfuse/promptfoo 可追技术层，但追不上产品层飞轮——它们的用例是人写的一次性资产，不是 CC 持续积累的活资产。

## Slogan / 电梯演讲

- **Tagline**：*Every change grows the suite. Every release runs it all.*（每次改动都在长用例，每次发版都跑全量。）
- **Slogan**：*The MCP-native test rig for AI agents.*
- **一句话**：Langfuse/promptfoo 解决「评测 agent」，AgentRig 解决「让编码工具在开发循环里直接跑 agent 回归」——前者是 CI/观测层，后者是 agent 的开发时护栏。
- **完整定位**：*Run your agent's regression suite from Claude Code, Codex, or any MCP client. Build test scenarios from production sessions, replay them with a 4-layer mock stack, and let your coding agent own its own regression loop.*

## 核心定位（sharpen）

> **AgentRig = 帮你给「业务 agent」搭的回归测试台；编码工具（CC/Codex）通过 MCP 在开发循环里自动驱动它。**

### 三层角色（务必区分，定位就靠它）

| 角色 | 谁 | 做什么 |
|------|-----|--------|
| **被测对象（SUT）** | 业务 agent（垂直领域：图像编辑、客服、RAG、数据分析…） | AgentRig 跑回归测的东西 |
| **测试驱动者** | 编码工具 CC/Codex（通过 MCP） | 写业务 agent 代码时，调 AgentRig 跑回归 |
| **测试平台** | AgentRig | 用例管理 + 四层 mock + 机判 + MCP 工具开放 |

⚠️ **关键澄清**：AgentRig **不测编码工具本身**。CC/Codex 是驱动者不是被测对象；被测的是开发者用 CC 正在写的那个**业务/垂直 agent**。

### 工作闭环（5 步）

1. 开发者用 CC/Codex 改**业务 agent**的代码
2. CC 通过 MCP 工具查 AgentRig 用例库 → 按改动相关性挑/建场景
3. AgentRig **跑场景**（四层 mock 回放：L0 内联 → L1 剧本 → L1.5 参数等价变形 → L2 样本库 → L3 模拟器）
4. **机判**（rule_judge + arg_assert + preference_judge）+ 结论**回写**用例
5. 生产会话三级切分（run→turn→case）持续反哺用例库

**关键差异**：驱动者从「人 + CI」（Langfuse/promptfoo 模式）变成「**编码工具在开发循环里**」——不是人去平台点测试，是 CC 写完业务 agent 的代码，顺手驱动 AgentRig 把这个业务 agent 的回归跑了。

## 核心差异化：工具层测试 vs 对话层观测

AgentRig 和 Langfuse/promptfoo 的本质分界 —— **测试层不同**：

| | Langfuse / promptfoo | AgentRig |
|---|---|---|
| 测试层 | 对话层 / 输出层（看 agent 最终说了/做了什么） | **工具层**（MCP proxy，工具调用从它过） |
| 能 mock 工具 | ❌ 只观测不干预 | ✅ 选择性 mock 任意工具 |
| 能断言工具调用 | ⚠️ 事后看 | ✅ 该不该调 / 参数 / 顺序 |
| 回归稳定性 | 工具真实返回，会抖动 | ✅ 控制变量 = 稳定回归 |

**为什么是现在**：MCP 之前工具调用各 agent 私有，工具层测试不可能标准化；MCP 把工具调用标准化后，**「工具层测试」第一次成为独立、通用、标准的层**。AgentRig 占这个层 —— 不是「又一个 eval 工具」，是「MCP 让工具层可测」这件事的第一个产品。详见 `06-测试执行模型与协议适配.md`。

## 三大差异化护城河

1. **MCP 反向开放（最独特）** —— 不是「测 MCP server」，而是「把测试平台能力包装成 MCP 工具，让 CC/Codex 驱动」。目前无竞品做这个方向。
2. **工具版本管理 + 提示词版本管理（同构双 manager）** —— Langfuse 只管 prompt；AgentRig 把「被测 agent 的工具定义」也纳入版本管理，对「工具会变的 agent」是刚需。
3. **四层 mock 体系**（尤其 L1.5 参数等价变形 + L3 模拟器）—— mcp-eval 明确反 mock（走真实调用），promptfoo 只有简单 mock。

## 支持哪些 agent（接入边界）

AgentRig 通过 `AgentTransport` adapter 接入被测 agent，支持**任何有 tool-calling 往返的 agent**（覆盖主流：MCP / OpenAI tool-calling / Anthropic tool_use / LangGraph / 自研协议）。mock 注入的本质是「平台做 tool-calling 中间人，实时回灌 tool_result」。详见 `06-测试执行模型与协议适配.md`。

- **MCP agent**：首选接入。AgentRig 作为 MCP server 提供工具，mock 是工具实现的天然分支，零 hack。
- **其他 tool-calling agent**（OpenAI/Anthropic/LangGraph…）：平台作为 tool 中间人，写 transport adapter。
- **非 tool-calling agent**：退化为纯观测模式（不能 mock）。

> AgentRig 不是「只能测 MCP agent」，但 MCP 是最优雅、最值得倡导的接入方式（和 MCP-first 定位闭环）。

## 我们不是什么（避免定位漂移）

- ❌ 不是又一个 LLM eval 框架（promptfoo/DeepEval 已够好）
- ❌ 不是又一个观测平台（Langfuse 已是巨头）
- ❌ 不是测 MCP server 的工具（mcp-eval 已占）
- ✅ 是「让编码工具自己驱动 agent 回归」的那一层 —— 唯一定位
