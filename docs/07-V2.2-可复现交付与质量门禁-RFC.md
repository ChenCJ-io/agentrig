# AgentRig V2.2：可复现交付、质量度量与发布门禁 RFC

> RFC ID：AR-RFC-0001
>
> 状态：Proposed
>
> 版本：0.1
>
> 日期：2026-08-07
>
> 目标里程碑：GOAI 2026 初赛交付、复赛工程包与后续产品化
>
> 前置架构：`00-总体架构.md`
>
> 前置实现：`06-V2.1-基于证据的自适应评测闭环-开发设计.md`

本文定义 AgentRig 在 V2.1 之后的优化路径。重点不再是继续增加横向功能，而是把当前已经实现的
AgentTeams 多 Agent 评测闭环升级为公开可复现、结果可量化、运行可观测、发布可门禁的工程产品。

本文经评审接受后，作为 V2.2 的实施和验收依据；在接受前不改变 V1/V2/V2.1 的权威契约。

---

## 0. 决策摘要

V2.2 采用“证据优先的交付强化”路线，按以下顺序实施：

1. **先完成可复现发布**：公开参考 Target、一键环境、版本清单、正式 Release 和干净机器验收。
2. **再完成可量化证明**：从已有 RunEvent、Evaluation、DecisionRecord 和 AgentInvocation 派生质量报告。
3. **随后完成发布门禁**：复用现有 A/B CaseRun 配对，形成确定性的 comparison report 和 gate verdict。
4. **并行补齐可信度**：真实后端 E2E、Skill 契约检查、故障注入和可选 OpenTelemetry。
5. **生产化增强后置**：Kubernetes、OIDC/RBAC、多租户隔离和大规模性能优化不进入初赛关键路径。

本 RFC 不新增第二套 Run、CaseRun 或证据存储。质量指标、A/B 对比和门禁必须从现有不可变运行事实
派生；OpenTelemetry 只作为观测投影，不成为业务事实来源。

## 1. 背景与当前基线

### 1.1 已有可复用能力

当前代码已经具备：

- Manager、Simulation Curator、Evidence Judge 三个不同 Agent 身份；
- AgentTeams/Matrix 的真实请求、响应和 AgentInvocation 记录；
- AssistantSession、EvaluationPlan、DecisionRecord、Run、CaseRun、RunEvent 和 Evaluation 完整链路；
- 成功、策略失败、超时恢复三类真实运行证据；
- A/B Target 角色、`comparison_pair_id` 和 `comparison_role`；
- `duration_ms`、`ttft_ms`、usage、request ID 等原子运行事件；
- JSON、Markdown、HTML 报告和脱敏导出基础；
- Python 3.12/3.13、前端、PostgreSQL、wheel smoke test 和依赖审计 CI；
- 11 个 AgentRig/AgentTeams Skill，其中 V2 Skill 已声明稳定 contract version。

因此，V2.2 的主要工作是把已有原子能力组合成可交付产品，不重写执行内核。

### 1.2 当前主要缺口

#### A. 公开复现仍依赖私有被测项目

完整现场链路当前以本机 lassist 为被测对象。仓库不应包含 lassist 私有业务代码，但缺少公开参考
Target 会使外部评审无法在干净环境中独立重现完整协议、工具调用、规则判定和恢复场景。

#### B. 有原始指标，没有统一质量报告

运行事件已保存耗时、首 token 延迟和 usage，DecisionRecord 也已有成功率与 provenance 指标，但这些
数据尚未聚合成稳定的质量报告，无法直接回答效率、成本、稳定性和版本回归问题。

#### C. A/B 执行已存在，发布决策尚未产品化

同一个 Run 已能展开 baseline/candidate 配对，但尚无统一 ComparisonReport、阈值策略和
pass/warn/fail/inconclusive 门禁结果。

#### D. 自动化可信度存在两处明显空白

- 当前 Playwright 用例主要 Mock `/api`，可验证 UI 契约和无障碍，但不能证明浏览器到真实 FastAPI、
  数据库和 Target 的完整链路；
- 前端覆盖率门禁当前只覆盖少量纯函数，不能解释为整个 Web 产品的覆盖率。

#### E. Skill 版本可见，但缺少分发级契约校验

Skill contract version 目前写在 Markdown 中，尚无统一 manifest、角色/工具权限验证、示例 fixture
校验和 package compatibility report。

#### F. 运维证据不足

当前有结构化业务事件和普通日志，但没有标准 OTLP Trace/Metric 导出，也没有统一 correlation context。

### 1.3 非代码因素

提交清单中的正式 Release/Tag、公开仓库链接、演示视频、凭据轮换和干净机器验收仍需闭环。最近一次
CI 异常发生在 GitHub Runner 获取 Action 的基础设施阶段；代码质量、Python 后端和前端任务已成功。
实施时应先重跑 CI，只有同一仓库步骤重复失败时才修改工作流。

## 2. 目标、非目标与约束

### 2.1 P0：初赛交付目标

1. 不依赖 lassist 私有代码即可运行公开参考 Target，并分别提供确定性 CI 与真实 AgentTeams 验收模式。
2. 一条命令完成环境预检、启动、种子数据、场景执行、验证和脱敏证据导出。
3. Release 可追溯到 Git SHA、依赖锁、AgentTeams 版本、镜像摘要、配置哈希和场景 Run ID。
4. 形成至少成功、策略回归、故障恢复三种演示结果。
5. 形成实测的效率、稳定性、证据完整率和资源消耗报告，不使用估算数据冒充实测。
6. 通过密钥扫描、构建产物扫描和干净机器验收后再公开发布。

### 2.2 P1：复赛工程目标

1. 生成稳定的 `QualityReport`、`ComparisonReport` 和 `ReleaseGateResult` 契约。
2. 支持可选 OpenTelemetry Trace/Metric 导出，关闭时不改变任何执行语义。
3. 提供至少一条浏览器到真实后端、数据库和参考 Target 的 CI E2E。
4. 为全部 Skill 建立 machine-readable manifest 和契约一致性检查。
5. 通过确定性故障注入验证超时、重复事件、乱序事件、无效引用和恢复行为。

### 2.3 P2：产品化目标

- PostgreSQL 生产部署和容量基线；
- Kubernetes/Helm 参考部署；
- OIDC、RBAC、工作区隔离和外部 Secret backend；
- 长周期漂移趋势、历史基线和组织级发布策略；
- 大规模并发、背压和成本预算治理；
- 在行为测试冻结以后拆分高复杂度后端服务和前端页面。

### 2.4 明确非目标

V2.2 不做：

- 新建通用工作流/DAG 引擎；
- 用新的“质量运行”对象替代 Run/CaseRun；
- 为演示伪造 AgentTeams/Matrix 协作回执；
- 把 lassist 私有实现复制进公开仓库；
- 让 OpenTelemetry 后端参与业务判定；
- 追求没有风险意义的全仓 100% 覆盖率；
- 在初赛前重写 `RunExecutor`、Target Chat 或整个产品页面；
- 在样本量不足时把波动性指标当作阻断式门禁；
- 保存模型隐藏思维过程、明文 Secret 或未脱敏业务消息。

### 2.5 兼容约束

- V1 MCP 原子工具及 Run/CaseRun 状态语义保持兼容；
- V2.1 DecisionRecord、确认和权限边界保持兼容；
- 原有 `agentrig.run-report.v1` 和 `agentrig.competition-evidence.v1` 不原地改变字段语义；
- 新报告优先通过新增契约实现，旧客户端无需同步升级；
- SQLite 继续作为本地体验，PostgreSQL 继续作为并发和生产参考数据库。

## 3. 成功指标

### 3.1 P0 验收指标

| 指标 | 目标 | 验证方式 |
|---|---:|---|
| 干净机器启动成功率 | 支持的验收环境全部成功 | 至少 Ubuntu CI 与一台全新本机环境 |
| Reference CI 一致性 | 20/20 verdict 相同 | 无外部模型、Rule 主评判的确定性 suite |
| 策略回归检出率 | 20/20 检出 | Reference CI 的 baseline/candidate 固定故障版本 |
| 真实多 Agent 证据 | 成功/失败各至少 1 条 | 真实 Manager、Curator、Judge 与 Matrix 回执 |
| 证据 provenance 完整率 | 100% | Decision、Invocation、Evaluation 引用校验 |
| Release 产物可追溯率 | 100% | manifest 中 SHA/版本/哈希/Run ID 齐全 |
| 明文敏感信息 | 0 | Git 历史、工作区、产物和证据包扫描 |
| 核心 CI | 全绿 | Python、质量、前端、PostgreSQL、package |

### 3.2 P1 验收指标

| 指标 | 目标 | 说明 |
|---|---:|---|
| 真实后端 E2E | 每个 PR 至少 1 条 | 浏览器不 Mock 核心 API |
| Skill 契约校验 | 11/11 通过 | contract、role、allowed tools、schema、package |
| OTLP 故障隔离 | 100% | Collector 不可达时 Run 仍按原语义完成 |
| A/B 配对完整率 | 100% 或明确 skipped | 不允许静默丢 pair |
| Gate 可重放性 | 同一快照结果一致 | 相同 Run + policy hash 得到相同 verdict |
| 故障恢复证据 | 预置故障全部有终态 | 无无限重试、无覆盖旧 Attempt |

### 3.3 指标解释原则

1. 确定性 Reference CI 和真实 AgentTeams/模型场景必须分栏报告，不能混合统计。
2. 真实模型样本少于 20 次时，p95 仅展示为观察项，不作为阻断门禁。
3. 成本只有在保存模型标识和价格快照时才计算；否则只报告 token usage。
4. 基础设施故障必须标为 `inconclusive` 或 `evaluation_error`，不能记为 candidate 产品失败。
5. 所有百分比同时展示分子、分母和缺失项。

## 4. 总体方案

```text
                           ┌─────────────────────────────┐
                           │ Release Manifest / SBOM      │
                           │ Benchmark / Evidence Bundle │
                           └──────────────▲──────────────┘
                                          │ derive
┌──────────────┐  HTTP/SSE  ┌─────────────┴──────────────┐  OTLP   ┌──────────────┐

                                 ┌────────▼─────────┐

                                 │ Manager/Workers  │
```

### 4.1 数据权威关系

| 信息 | 权威来源 | 其他系统的角色 |
|---|---|---|
| 执行状态和证据 | AgentRig Run/CaseRun/Event | Trace 仅投影 |
| Agent 委派结果 | AgentInvocation + Matrix ID | 日志仅辅助排障 |
| 语义判定 | Evaluation | QualityReport 聚合 |
| 决策依据 | DecisionRecord | UI/报告展示 |
| A/B 配对 | `comparison_pair_id/role` | ComparisonReport 派生 |
| 发布策略 | 版本化 ReleasePolicy 文件 | CLI/API 读取 |
| 发布结论 | Run snapshot + policy hash | 可重放、可导出 |

## 5. 工作流 A：公开可复现发布

### 5.1 Public Reference Target

新增 `examples/reference_target/`，实现现有 Driver 所需的最小会话、SSE、tool-call、tool-result、usage
和终态契约。该服务必须满足：

- 无外部模型、无外部网络依赖；
- 固定 seed，同一输入得到同一事件序列；
- 支持显式版本 `baseline` 与 `candidate-regression`；
- 只实现公开协议，不复刻 lassist 内部逻辑；
- 事件中提供稳定 request ID，但不把固定 ID 当作业务断言；
- 可通过配置精确启用故障，禁止随机注入。

建议内置三个场景：

| 场景 | Target 行为 | 预期验证 |
|---|---|---|
| `reference_success` | 请求工具、接收受控结果、完成回答 | CI 为 Rule pass；完整模式另有 Judge pass 和 Worker 回执 |
| `reference_policy_regression` | candidate 跳过确认直接调用工具 | baseline pass、candidate fail、门禁 fail |
| `reference_recovery` | 首次返回受控 503 或超时，确认后创建新 Run 恢复 | 旧 Attempt 保留、不擅自无限重试、终态可解释 |

Reference Target 是公开复现基线；真实 lassist 场景继续作为更复杂的补充证据，两者不得互相替代或
混写结果。

同一个 Reference Target 提供两种验收 Profile：

| Profile | 外部模型 | 用途 | 是否证明三 Agent 协作 |
|---|---|---|---|
| `reference-ci` | 不需要 | 使用 fixture/sample 与 Rule 验证协议、证据、A/B 和门禁确定性 | 否 |
| `reference-agentteams` | 通过 `env:` 提供 | 使用真实 Manager、Curator、Judge 和 Matrix 完整验收 | 是 |

20 次一致性与性能门禁使用 `reference-ci`；比赛多 Agent 证据使用 `reference-agentteams`，并保存每次
真实结果，而不是要求模型输出绝对确定。公开可复现意味着代码、协议、配置和步骤公开，不负责替
使用者提供第三方模型凭据。

### 5.2 一键操作入口

新增统一入口，建议命令契约为：

```bash
scripts/reference_demo.sh all --profile reference-ci
scripts/reference_demo.sh all --profile reference-agentteams
scripts/reference_demo.sh setup
scripts/reference_demo.sh verify
scripts/reference_demo.sh run --scenario all
scripts/reference_demo.sh evidence
scripts/reference_demo.sh down
```

`all` 依次执行 setup、verify、run 和 evidence。`reference-ci` 是默认 CI/干净机器入口；
`reference-agentteams` 是比赛完整验收入口。其余子命令用于开发调试和失败后的有界恢复。

`setup` 必须：

1. 检查 Docker、Python/uv、Node 和端口；
2. 在完整模式下安装或验证固定版本 AgentTeams，并检查所需 `env:` 模型凭据；
3. 启动 PostgreSQL、AgentRig、Reference Target 和所需协作组件；
4. 生成仅包含 `env:` 引用的配置；
5. 幂等执行数据库迁移和种子数据；
6. 输出下一条可执行命令，不输出 Secret。

`verify` 必须实际检查 HTTP health、数据库 migration、三个 Agent 身份、角色 MCP token 隔离、Matrix
连通、Target capability 和前端入口。仅检查进程存在不算通过。

允许存在 `--core-only` 快速模式，但比赛完整验收不得使用该模式替代真实 AgentTeams 路径。

### 5.3 Release Manifest

新增独立的 `agentrig.release-evidence.v1`，组合现有 competition evidence，而不修改其 v1 语义：

```json
{

  "release": {
    "version": "0.x.y",
    "git_sha": "...",

  },

    {"path": "...", "sha256": "...", "media_type": "..."}
  ],
  "configuration": {
    "public_config_hash": "sha256:...",
    "secret_values_included": false
  },
  "scenarios": [
    {"name": "...", "run_id": "...", "expected": "...", "actual": "..."}
```

Manifest 生成失败必须阻止 Release；未知版本不得用 `latest` 或空字符串代替。

### 5.4 Release 产物

P0 正式 Release 至少包含：

- wheel 与 sdist；
- release manifest 与 SHA256SUMS；
- Reference Target 镜像或可重复构建信息；
- competition evidence bundle；
- benchmark JSON 与 Markdown 摘要；
- SBOM；
- 安装、升级、卸载和已知限制说明。

P1 Release 另行增加 Skill contract report、QualityReport、ComparisonReport 和 ReleaseGateResult。

GitHub Release workflow 必须在创建 Release 前完成 tag/version 一致性、核心测试、产物扫描和隔离安装
smoke test。对 GitHub Runner 的外部故障允许重跑，不允许通过跳过核心 job 获得绿色状态。

### 5.5 安全发布检查

发布前执行：

- 当前工作区和完整 Git 历史 Secret 扫描；
- wheel、sdist、前端构建物、截图、日志和 JSON 证据包扫描；
- 比赛专用模型 Key 和协作 token 轮换；
- SBOM 和高危依赖审计；
- 公开配置只允许 `env:VARIABLE_NAME` Secret 引用；
- 在不包含开发机缓存和本地数据库的环境中安装并复核。

## 6. 工作流 B：质量报告与可观测性

### 6.1 QualityReport

在现有 ReportingService 上新增 `agentrig.quality-report.v1`。它只从一个终态 Run 及其完整 CaseRun
分页、RunEvent、Evaluation 和关联 Invocation 派生，不新增业务表。

最小结构为：

```text
QualityReport
├─ run identity and frozen scope
├─ outcomes
│  ├─ pass/fail/inconclusive/evaluation_error
│  └─ skipped/cancelled/interrupted
├─ latency
│  ├─ run duration
│  ├─ CaseRun p50/p95
│  ├─ driver duration p50/p95
│  └─ TTFT p50/p95
├─ usage
│  ├─ input/output/total tokens
│  └─ estimated cost + pricing snapshot（可选）
├─ reliability
│  ├─ retry count/rate
│  ├─ timeout/error code distribution
│  └─ recovery success rate
├─ collaboration
│  ├─ decision success/provenance rate
│  ├─ invocation completion/error rate
│  └─ curator/judge duration
└─ evidence_quality
   ├─ evaluation reference validity
   ├─ missing reference count
   └─ redaction status
```

新增接口：

```text
GET /api/runs/{run_id}/quality-report
GET /api/runs/{run_id}/quality-report?format=markdown
```

运行未终态时返回冲突错误；原始字段缺失时返回 `null + missing_fields`，禁止填零掩盖缺失。

### 6.2 Benchmark 方法

新增 `scripts/run_benchmark.py`，输出原始 JSON 和 Markdown，不把基准结果硬编码进 README。

执行规则：

1. 记录 Git SHA、主机、CPU、内存、Python/Node、数据库和组件版本；
2. 确定性 reference suite 预热 2 次，正式运行 20 次；
3. 真实 AgentTeams/模型场景至少运行 3 次，并明确标记小样本；
4. 每次使用新的 Run，不覆盖失败样本；
5. 保存每次原始结果和失败原因；
6. 计算值使用原始事件时间，不用 UI 计时；
7. 手工流程对比必须定义相同起止点和完成标准；
8. 不同硬件、模型或价格快照的结果不得直接合并。

初赛建议至少展示：首次可用时间、单场景总耗时、证据引用完整率、重复结果一致性、失败恢复率和
token usage。人工与 AgentRig 对比只使用现场实际计时结果。

### 6.3 OpenTelemetry 接入

可观测性采用可选依赖和 no-op 默认实现。建议新增配置：

```toml
[observability]
enabled = false
service_name = "agentrig"
otlp_endpoint = "http://127.0.0.1:4318"
export_traces = true
export_metrics = true
sample_ratio = 1.0
```

建议 span：

| Span | 父级 | 关键属性 |
|---|---|---|
| `agentrig.run` | root | status、target count、case count |
| `agentrig.case_run` | run | driver、version、comparison role、status |
| `agentrig.driver.request` | case_run | driver type、status、duration、TTFT |
| `agentrig.provider.attempt` | case_run | provider、attempt、status、error code |
| `agentrig.agent.invocation` | case_run/session | agent role、status、retryable |
| `agentrig.evaluation` | case_run | evaluator、outcome、reference count |

统一 correlation 字段：

```text
trace_id, session_id, turn_id, decision_id, plan_id,
run_id, case_run_id, invocation_id, request_id
```

ID 可作为 span/log 属性，但不能作为 Metric label。Metric label 只允许低基数字段，如 driver、provider、
agent_role、evaluator、status 和 error_code。

建议 Metric：

- `agentrig_runs_total`；
- `agentrig_case_runs_total`；
- `agentrig_case_run_duration_ms`；
- `agentrig_driver_duration_ms`；
- `agentrig_driver_ttft_ms`；
- `agentrig_provider_attempts_total`；
- `agentrig_agent_invocations_total`；
- `agentrig_agent_invocation_duration_ms`；
- `agentrig_evaluations_total`；
- `agentrig_usage_tokens_total`。

### 6.4 故障隔离与隐私

- Collector 不可达只记录限频 warning，不得使 Run 失败；
- exporter queue 必须有界，应用关闭时 flush 有超时；
- span/log 不包含 prompt、完整 response、Secret、Cookie、Matrix token 或工具结果正文；
- 采样不影响 AgentRig 数据库中的业务证据完整性；
- Trace 链接回 AgentRig 资源，AgentRig 不依赖 Trace 恢复状态。

## 7. 工作流 C：A/B Comparison 与发布门禁

### 7.1 复用现有 A/B 模型

当前 `RunCasesRequest` 已支持最多两个 Target，并要求 `baseline` 和 `candidate` 成对；Planner 已为每个
配对生成 `comparison_pair_id`。V2.2 直接聚合这些 CaseRun，不创建新 Run 类型。

### 7.2 ComparisonReport

新增 `agentrig.comparison-report.v1`：

```text
ComparisonReport
├─ run_id / generated_at / source_hash
├─ pair_summary
│  ├─ total/comparable/skipped/incomplete
│  ├─ regressions/fixes/unchanged
│  └─ execution_errors
├─ outcome_delta
├─ duration_delta
├─ TTFT_delta
├─ usage_delta
├─ evidence_delta
└─ pairs[]
   ├─ comparison_pair_id / case_id / repeat_index
   ├─ baseline outcome + refs
   ├─ candidate outcome + refs
   ├─ classification
   └─ metric deltas
```

配对分类固定为：

- `unchanged_pass`；
- `unchanged_fail`；
- `regression`：baseline pass，candidate fail；
- `fix`：baseline fail，candidate pass；
- `changed_inconclusive`；
- `infrastructure_error`；
- `incomplete_pair`。

不得把执行错误自动归类为产品 regression。

新增接口：

```text
GET /api/runs/{run_id}/comparison-report
GET /api/runs/{run_id}/comparison-report?format=markdown
```

非 A/B Run 返回明确的 validation error，不返回空成功报告。

### 7.3 ReleasePolicy

第一阶段使用仓库内版本化策略文件，不新增数据库策略表：

```json
{
  "schema_version": "agentrig.release-policy.v1",
  "name": "competition-reference",
  "minimum_comparable_pairs": 1,
  "blocking": {
    "max_outcome_regressions": 0,
    "max_infrastructure_errors": 0,
    "min_evidence_reference_validity": 1.0,
    "min_decision_provenance_link_rate": 1.0
  },
  "warnings": {
    "max_duration_regression_ratio": 0.15,
    "max_token_regression_ratio": 0.10
  },
  "statistical_requirements": {
    "minimum_latency_samples": 20
  }
}
```

策略字段必须有上下界、默认单位和 schema 校验。比例统一使用 `[0, 1]`，展示层再转百分比。

### 7.4 ReleaseGateResult

`ReleaseGateResult` 是 `ComparisonReport + QualityReport + ReleasePolicy` 的纯函数结果：

```text
verdict: pass | warn | fail | inconclusive
policy_hash
source_run_id
source_snapshot_hash
checks[]:
  name, severity, actual, threshold, outcome, evidence_refs
```

规则：

1. 任何 blocking check 失败，结果为 `fail`；
2. 只有 warning 失败，结果为 `warn`；
3. 配对不足、关键字段缺失或基础设施错误无法归因时，结果为 `inconclusive`；
4. `inconclusive` 不得被 CI 当作 pass；
5. 相同 Run snapshot 与 policy hash 必须得到完全一致的结果。

CLI：

```bash
agentrig gate evaluate \
  --run-id run_xxx \
  --policy configs/release-policies/competition-reference.json \
  --output .agentrig/release-gate.json
```

CLI 退出码：`pass=0`、`warn=0`、`fail=2`、`inconclusive=3`。是否把 warn 视为 CI 失败由调用方决定。

### 7.5 Web 产品流程

Run 详情页新增一个“版本对比”区域：

- 顶部显示 gate verdict、策略名和 policy hash；
- 展示 regression/fix/unchanged/infrastructure error 数量；
- 每个 pair 可展开 baseline/candidate 原子证据；
- latency/token 小样本明确标记“仅观察”；
- 失败 check 直接链接到 CaseRun、Event、Evaluation 或 Invocation；
- 提供 JSON/Markdown 下载，不通过前端重新计算。

## 8. 工作流 D：测试、Skill 与恢复可靠性

### 8.1 测试分层

V2.2 明确四层自动化：

| 层级 | 范围 | 触发 |
|---|---|---|
| Unit/Contract | schema、策略、聚合纯函数 | 每个 PR |
| Backend integration | FastAPI、数据库、迁移、Reference Target | 每个 PR |
| Browser real-backend E2E | Browser → FastAPI → DB → Reference Target | 每个 PR |
| AgentTeams live acceptance | Manager/Matrix/Workers/可选模型 | nightly、手动、Release |

现有 Mock API Playwright 测试继续保留，但定位为 UI contract/accessibility test，不能替代 real-backend
E2E，也不能在报告中称为完整端到端测试。

### 8.2 真实后端 E2E

新增独立 Playwright project：

1. 启动临时 SQLite 或 PostgreSQL；
2. 启动真实 FastAPI 和 Reference Target；
3. 通过公开 API 幂等 seed 资产；
4. 浏览器创建或打开评测计划并提交；
5. 等待 Run 终态；
6. 验证 Run、CaseRun、Evidence、Report 的真实链接；
7. 测试结束清理临时环境。

每 PR 的 E2E 不强制依赖真实外部模型。AgentTeams live acceptance 单独证明真实多 Agent 路径，避免
外部服务波动把每个 PR 的确定性质量门禁变成随机信号。

### 8.3 覆盖率策略

不立即设置虚假的全仓高阈值。实施顺序：

1. 记录 Python 与 Web 的真实全量基线；
2. 将当前局部覆盖率明确标注为 scoped coverage；
3. 新增/修改的质量报告、门禁策略和 manifest 代码达到至少 90% branch coverage；
4. 核心安全策略、Schema 和纯聚合函数必须 100% 覆盖已声明分支；
5. 全仓覆盖率不得无解释下降，阈值在获得稳定基线后单独评审。

覆盖率只是回归信号，不能代替 Reference Target 和 live acceptance。

### 8.4 Skill Manifest

新增 `skills/manifest.json`，每项至少包含：

```text
id, name, role, path, contract_version,
allowed_tools, input_schema, output_schema,
example_fixtures, compatible_agentrig, compatible_agentteams
```

自动检查：

- Skill ID、name 和 contract version 唯一；
- manifest 与 `SKILL.md` 声明一致；
- 相对引用和 JSON Schema 存在且有效；
- allowed tools 在对应角色 MCP 中存在；
- Manager、Curator、Judge 不获得跨角色写工具；
- 示例输入输出通过 schema；
- AgentTeams package builder 包含正确 Skill，并记录 manifest hash；
- 版本不兼容时构建直接失败，不静默忽略。

Release 输出 `agentrig.skill-contract-report.v1`，作为比赛 Skill 工程证据。

### 8.5 确定性故障注入

Reference Target、Matrix fake transport 和 Agent invocation 测试夹具支持显式故障计划：

- 第 N 次请求超时或返回 503；
- 重复 Matrix event；
- Matrix event 乱序；
- Worker 超过 deadline 回写；
- Curator 输出 schema 无效；
- Judge 引用不存在或不属于当前 CaseRun 的 Event；
- Run 取消与 Worker 回执竞态；
- OTLP Collector 不可达。

每个故障必须验证：终态、error code、retryable、重试上限、旧 Attempt 保留、无重复副作用和用户可见
恢复建议。故障注入只在显式测试配置中启用。

## 9. API、Schema 与迁移策略

### 9.1 新增稳定契约

| 契约 | 版本 | 是否持久化 |
|---|---|---|
| ReleaseEvidence | `agentrig.release-evidence.v1` | 产物文件 |
| QualityReport | `agentrig.quality-report.v1` | 否，派生 |
| ComparisonReport | `agentrig.comparison-report.v1` | 否，派生 |
| ReleasePolicy | `agentrig.release-policy.v1` | 仓库配置 |
| ReleaseGateResult | `agentrig.release-gate.v1` | 产物文件，可重放 |
| SkillContractReport | `agentrig.skill-contract-report.v1` | 产物文件 |

### 9.2 第一阶段不新增数据库表

P0/P1 优先从已有不可变事实派生报告。只有出现以下需求时，才另立 RFC 增加持久化表：

- 组织级策略管理、审批和权限；
- 历史趋势查询需要预聚合；
- ReleaseGate 需要签名、审批或状态机；
- 多租户保留策略不同。

### 9.3 Snapshot Hash

报告的 `source_snapshot_hash` 必须由稳定序列化后的以下内容计算：

- Run 冻结快照；
- 全部 CaseRun 摘要；
- 参与聚合的 Evaluation 和相关 RunEvent ID/Hash；
- 关联 DecisionRecord/AgentInvocation 的稳定字段。

生成时间、展示文本、数据库行顺序不得影响 hash。Hash 算法固定为 SHA-256，并在 schema 文档中说明
canonicalization 规则。

## 14. 发布、灰度与回滚

### 14.1 灰度原则

- Quality/Comparison API 为新增只读接口；
- OpenTelemetry 默认关闭，通过配置逐环境开启；
- Release Gate 先以报告模式运行，再进入 blocking CI；
- warning 阈值至少观察一个稳定周期后才升级为 blocking；
- Reference Target 与 lassist Target 使用不同 ID、Profile 和证据目录。

### 14.2 回滚

- 关闭 `observability.enabled` 即可回滚 telemetry，不需要数据迁移；
- Gate CLI/接口异常时回滚到前一版本，Run 数据不受影响；
- 报告是派生对象，不删除或改写 Run/CaseRun；
- 新 schema 只增不改，旧报告接口继续可用；
- Release 产物不可覆盖，同一版本不得重新上传不同字节；
- 发现凭据泄露时立即撤销 Release、轮换凭据并发布新版本，不复用已暴露版本号。

## 15. 被否决的替代方案

### 15.1 初赛前优先建设 Kubernetes

否决原因：不能直接解决外部评审无法复现、缺少量化数据和没有正式 Release 的问题，且会增加部署
变量。Compose/一键脚本先形成稳定基线，Helm 在 P2 补齐。

### 15.2 只使用 lassist 作为唯一 Demo Target

否决原因：真实度高，但公开复现依赖私有项目和模型环境。采用“公开确定性基线 + 私有业务真实证据”
双轨方式更可验证。

### 15.3 新建独立 Benchmark Run 数据模型

否决原因：会复制执行状态、证据和评判，产生事实冲突。Benchmark、Quality 和 Gate 都从现有 Run
派生。

### 15.4 用 Trace 后端作为审计真相

否决原因：采样、网络和保留策略会导致 Trace 不完整。AgentRig 数据库继续保存权威业务事实。

### 15.5 先重构所有大文件

否决原因：在提交窗口内收益低、回归面大。先补 E2E 和契约测试，再按变更热点拆分。

## 16. 评审决策点

接受本 RFC 等于接受以下决策：

1. Public Reference Target 是公开复现基线，lassist 是补充 live evidence。
2. P0 不建设 Kubernetes、企业 RBAC 或新的工作流引擎。
3. Quality、Comparison 和 Gate 从现有不可变事实派生。
4. OpenTelemetry 可选且不得影响业务状态。
5. A/B Release Gate 首先使用仓库内版本化 policy，不新增数据库表。
6. Mock UI E2E 与 real-backend E2E 分层命名和统计。
7. 所有 11 个 Skill 进入统一 manifest 和 contract report。
8. 真实模型小样本不作为阻断式性能门禁。

仍需项目负责人确认但不阻塞技术实施的问题：

- 首个正式公开版本号；
- 仓库转公开的准确时间与视频托管位置；
- live benchmark 的模型调用预算；
- 决赛阶段优先选择 Helm、企业鉴权还是历史趋势能力。

默认值为：版本号在首次 Release 前统一决定；公开时间安排在 Secret scan 和干净机验收之后；live
benchmark 控制在 3—5 次；决赛优先级由复赛反馈决定。

## 17. 建议实施顺序

```text
重跑 CI
  → Secret scan / 版本冻结
  → Public Reference Target
  → 一键环境与 clean-machine 验收
  → ReleaseEvidence + Benchmark
  → 正式 Release / 视频 / 初赛提交
  → QualityReport
  → ComparisonReport + ReleaseGate
  → OTLP + real-backend E2E + Skill contract
```
