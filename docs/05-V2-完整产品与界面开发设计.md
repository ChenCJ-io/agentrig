# AgentRig V2 完整产品与界面开发设计

> 状态：已实现的开发与验收基线
> 版本：2.0
> 日期：2026-08-03
> 前置架构：`03-V2-智能评测助手与AgentTeams-开发设计.md`
> 视觉参考：本机 AgentScope 平台的信息架构、工作台布局和 Optical Console 设计语言

本文把 AgentRig V2 从“已经跑通的三 Agent 评测链路”提升为“可持续管理多个被测 Agent 的
智能评测平台”。本文是产品结构、页面设计、前后端实现和浏览器验收的直接依据；V1/V2 已有
领域语义、权限边界和执行链仍以 00-04 文档为准。

AgentScope 作为产品骨架参考，AgentRig 作为评测能力内核。复用的是成熟的信息架构、工作台
模式、视觉语言和管理流程，不复制品牌、私有素材或与 AgentRig 无关的 Pixcake 业务代码。

## 1. 产品结论

AgentRig V2 的定位确定为：

> 以被测 Agent（Target）为核心对象、以评测管理平台为主体、以智能评测助手为增强入口、
> 由 AgentTeams 承载 Evaluator Agents 协作的证据化智能评测平台。

它不是单一聊天页面，也不是通用多 Agent 编排器。完整业务主线为：

```text
接入 Target
  → 准备用例和工具结果资产
  → 用智能助手或人工方式生成评测计划
  → 人工确认
  → Run / CaseRun 执行
  → Manager / Curator / Judge 协作
  → Evidence 与 Evaluation 固化
  → 报告、对比和长期观测
  → 失败沉淀为 Case / Sample Draft
```

### 1.1 三类 Agent

| 类型 | 实例 | 产品含义 |
|---|---|---|
| 被测 Agent | lassist | Target，评测对象，不属于 AgentTeams Evaluator Team |
| 主控 Agent | Evaluation Manager | 面向用户的智能评测助手，生成和诊断评测计划 |
| 专业 Worker | Simulation Curator、Evidence Judge | 受限上下文中的工具结果生成与独立证据裁决 |

### 1.2 三类配置

| 配置 | 回答的问题 |
|---|---|
| Target | 被测 Agent 是谁、通过什么 Driver 和 Endpoint 连接 |
| Execution Profile | 本次评测如何处理工具、评判、并发和超时 |
| Evaluator Team | Manager、Curator、Judge 如何映射到 AgentTeams 身份和运行时 |

## 3. 全局交互模型

### 3.1 平台外壳

- 固定 60px 顶部栏和 232px 深色侧边栏；
- 顶部栏左侧展示 AgentRig 品牌和当前页面上下文；
- Target 工作区顶部固定展示 Target、环境、版本、Profile 和健康状态；
- 一级业务域与当前域二级目录分组显示，避免一次铺开全部页面；
- 画布使用浅灰背景，操作表面使用白色和细分割线；
- 页面只保留一个主要滚动容器，避免多层滚动冲突。

### 3.2 工作台模式

资产类页面统一采用：

```text
目录/筛选栏 → 高密度列表 → 详情与操作面板
```

执行类页面统一采用：

```text
运行摘要 → CaseRun 列表 → Evidence 时间线 → Verdict 面板
```

助手类页面统一采用：

```text
会话列表 → 自然语言与结构化卡片 → 计划/工作流/证据上下文
```

### 3.3 状态原则

- 执行状态和评测结论分开显示；`completed` 不等于 `pass`；
- 没有真实心跳时不显示 Worker `online`，使用 `ready/degraded/unavailable`；
- 当前没有指标值时显示“未采集”，不能显示为 0；
- 所有 AI 总结标注来源 Run 和“AI generated”，不能成为权威事实；
- `PASS / FAIL / INCONCLUSIVE` 是 V2 当前权威结果，不生成无定义的综合分数。

## 4. 页面设计

### 4.1 被测 Agent 目录

平台默认首页展示真实 Target，不伪造多个 Agent。lassist 卡片包含：

- 名称、描述、Driver 和协议；
- Environment、Version、健康状态和最近检查；
- 用例数量、最近 Run 和真实评测分布；
- “进入工作区”“对话验证”“发起评测”三个入口。

右侧展示平台活动和 Evaluator Runtime 摘要，AgentTeams 不抢占 Target 主视觉。

### 4.2 评测总览

总览是 Target 工作区默认首页，以最近真实 Run 为视觉中心：

- Target 状态与当前 Profile；
- 用例、已审核资产、正在运行任务和待处理事项；
- 最近 Run 的执行状态与 Evaluation Outcome 分布；
- 能力覆盖、Provider 使用、AgentTeams 任务进度；
- 失败、待审核 Case、Draft Sample 和运行错误的行动队列。

### 4.3 对话验证

对话验证是直接与 Target 交互的人工测试入口，与智能评测助手严格区分：

```text
用户 → lassist → ToolCall → AgentRig Provider Chain → ToolResult → lassist
```

页面包含会话列表、对话时间线和工具证据栏。支持把完整对话或选中 Turn 转为 TestCase Draft，
把真实工具结果转为 Sample Draft。第一阶段只保证默认 lassist Target 的本机单会话工作流。

### 4.4 智能评测助手

智能助手继续使用三栏工作台：

- 左栏：评测会话、状态和快捷模板；
- 中栏：用户消息、Manager 回复、Plan/Run/Result 结构化卡片；
- 右栏：Target、Profile、选案范围、AgentTeams 工作流和 Evidence。

只读检索可自动执行，创建 Run 前必须绑定真实用户确认事件。助手输出的 Plan、Run、Case、Sample
和 Report 都必须跳转到专业管理页面。

### 4.5 测试用例

TestCase 定义“测什么”，结构为基本信息、初始状态、多轮 Turn、Fixture、Assertion 和 Rubric。

- 列表支持能力、工具、审核状态、来源、版本、Evaluator 和最近结果筛选；
- 详情页包含定义、运行历史、Evidence 和审核记录；
- 默认使用结构化编辑器，原始 JSON 仅作为高级视图；
- `approved` 不可原地修改，修改通过“复制为 Draft”完成；
- 手工、对话、失败证据、智能助手和导入创建的内容一律先进入 Draft。

审核工作台使用候选队列、用例内容和审核检查三栏布局。Curator 和 Manager 不能批准用例。

### 4.6 工具结果资产

工具结果资产分为：

```text
覆盖总览 / Samples / 采集队列 / Fixtures 索引 / 匹配实验室
```

- Fixture 属于 Case Turn，全局页面只提供索引；
- Sample 是可审核、跨用例复用的结果资产；
- Curator Result 和 Real Tool Result 先作为候选证据，再转为 Draft；
- Sample 详情显示匹配参数、忽略路径、结果、版本、Schema、来源证据和命中历史；
- Provider 命中必须展示 Fixture/Sample/Curator/Real Tool 每一步的 hit/miss/error 原因；
- 多个同等具体 Sample 产生不同结果时判定冲突，不使用数据库随机顺序静默选择。

### 4.7 Target 与 Execution Profile

Target 详情包含概览、连接与版本、能力、工具、运行历史和配置变更。接入向导包含基本信息、
Driver、连接、能力发现和最小冒烟验证。

Execution Profile 负责 Tool Mode、Provider Chain、Primary Evaluator、模型、并发、超时和重复次数。
编辑器实时检查与 Target Driver 的能力兼容性。

本机 lassist 预置：

| Profile | Mode | Providers | Evaluator |
|---|---|---|---|
| Local Intelligent | controlled | fixture → sample → simulation_curator | evidence_judge |
| Deterministic Regression | controlled | fixture → sample | rule |
| Live Observation | observe_only | 无注入 | rule/evidence_judge |

### 4.8 Run 与 CaseRun Evidence

Run 详情包含总览、CaseRuns、AgentTeams、配置快照和报告。CaseRun 证据工作台使用三栏：

- 左：Turn、事件类型和错误大纲；
- 中：按 Turn 分组的 Evidence 时间线；
- 右：权威 Outcome、Evaluator、Criteria 和 Evidence Refs。

当前事件类型全部结构化展示：user_message、driver_request、driver_session、assistant_text、
assistant_message、tool_call、provider_attempt、tool_result、validation、usage 和 error。

Criterion 与 Event ID 双向联动。重跑区分“当前配置验证修复”和“冻结快照复现历史”。

### 4.9 Evaluator Teams

第一版只提供内置 `Default Evaluation Team`：Manager、Curator、Judge。允许管理 Identity、模型、
Prompt/Skill 版本、超时和启用状态，不建设任意 Agent 拖拽编排器。

页面展示：

- Matrix、AgentTeams Runtime 和身份映射健康度；
- 每个角色的输入、输出、权限和禁止项；
- Invocation 的 created → dispatched → running → terminal 生命周期；
- Input/Result Hash、Matrix Request/Response Event、Result Ref 和 Evaluation 关联；
- Curator 不可见 Rubric、Judge 只能引用本 CaseRun Evidence 的可见性证明。

### 4.10 版本对比

版本对比复用一个 Run 内 baseline/candidate CaseRun 和 `comparison_pair_id`，不建设第二套引擎。

- 相同 Case、Profile、Evaluator 和 Repeat Count 保证公平；
- 结果分类为 improved、regressed、unchanged、inconclusive 和 not comparable；
- Case 详情按 Turn 同步展示两侧 ToolCall、参数、Provider、ToolResult、回答和 Judge Criterion；
- Repeat Count 大于 1 时显示 stable pass、stable fail、flaky 和 inconclusive。

### 4.11 评测报告

V2 提供 Run Report 和 Comparison Report。报告是冻结沟通产物，不随 Dashboard 当前数据变化。

报告包含执行摘要、范围、结果分布、能力覆盖、主要失败、AgentTeams 摘要、配置快照和 Evidence
索引。HTML、Markdown 和 JSON Evidence Package 为第一阶段导出格式。

### 4.12 Observability 与问题中心

观测数据明确区分 AgentRig 原生评测数据和可选 Target 生产遥测。V2 必须真实提供：

- Evaluation Outcome、回归、Flaky、执行错误趋势；
- Provider 命中、Schema 错误和 Exhausted；
- AgentInvocation 成功、超时、耗时和 Evidence Ref；
- Case/Sample 审核、能力和工具覆盖；
- 带公式、分母、来源和维度的指标目录；
- 能下钻到 Run、CaseRun 和 Evidence 的问题检索；
- 脱敏数据导出。

趋势点必须携带 Case 数量、Case Set、Profile 和版本；不同测试集不能伪装成严格回归对比。

## 5. 视觉系统

### 5.1 设计目标

视觉关键词：专业、克制、密集、可审计、操作型。避免营销首页、霓虹科技感、满屏渐变、大量
圆角卡片和无意义图表。

### 5.2 核心 Token

```text
Canvas      #f1f3f2
Surface     #ffffff
Ink         #151719
Graphite    #252927
Muted       #59615d
Line        #d7ddd9
Cobalt      #2457f5
Success     #237a59
Warning     #955900
Danger      #b8403a
```

- 中文正文使用 Geist/Noto Sans SC/system-ui；
- 英文微标签和 ID 使用 IBM Plex Mono/SFMono；
- 4px 基础间距；
- 外层工作面、对话框和主要操作使用 4-6px 圆角；
- 嵌套内容优先使用分割线和浅色带，不重复套卡片；
- 状态优先使用圆点与文字，Badge 只用于需要独立扫描的标签。

### 5.3 响应式

- 1600×1000 为主要验收尺寸；
- 1280×900 不重叠、不截断主要操作；
- 小于 1180px 时右侧详情栏可折叠；
- 小于 960px 时显示桌面工作台提示，不强行压缩三栏；
- 对话验证单独支持窄屏阅读，管理后台不承诺完整移动端编辑。

## 9. V2 验收场景

### 9.1 平台进入

1. 打开 AgentRig，看到真实 lassist Target；
2. Target 健康状态、Driver、版本和资产数量来自 API；
3. 进入 lassist 工作区，顶部上下文一致。

### 9.2 智能评测闭环

1. 在智能评测助手选择默认成功样例；
2. Manager 创建结构化 Plan；
3. 用户确认并提交；
4. lassist 真实执行；
5. Curator 在无 Rubric 输入下生成合法结果；
6. Judge 引用真实 Event ID 裁决；
7. Run 详情和报告可下钻全部关联。

### 9.3 资产管理

1. 用例和 Sample 使用结构化详情而非仅 JSON；
2. Draft 可编辑，Approved 只读；
3. 审核操作调用真实 API；
4. Profile 显示 Tool Mode、Provider Chain 和模型；
5. Target 连接检查返回真实结果。

### 9.4 证据验收

1. Run 的执行状态和评测结论分开；
2. CaseRun 时间线按事件类型显示；
3. Provider Attempt、ToolResult 和 Validation 可展开；
4. Evaluation Criterion 能定位 Evidence Ref；
5. AgentInvocation 显示输入/结果 Hash 和 Matrix Event；
6. Snapshot 可查看且不包含明文密钥。

## 10. 最终交付口径

最终验收不是“页面数量”，而是以下体验：

> 用户进入一个完整、统一、可信的评测平台；选择真实 lassist Target，通过设计良好的助手或
> 管理工作台发起评测；系统真实执行并展示工具、Worker、Judge 和证据；所有结果可以管理、
> 回溯、比较、报告和沉淀。

如实现与本文冲突，以不破坏既有执行事实、权限隔离、人工确认、证据引用和快照可复现为最高
优先级。

### 10.1 当前实现验收结果

- Target、Case、Sample、Profile 已具备真实创建、编辑和删除工作流；
