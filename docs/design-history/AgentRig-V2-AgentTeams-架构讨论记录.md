## 记录规则

1. 每次只讨论一个会影响实现的核心问题。
2. 用户明确认可后，才写入“已确认设计决策”。
3. 尚未确认的建议只放在“当前待讨论”，不能作为开工依据。
4. 已经由 V1 实现并验收的事实不重新设计，除非 V2 出现明确冲突。
5. 不在讨论过程中提前输出大而全的最终方案；用户要求后再整理完整架构和代码设计。
6. 代码名只在确实需要稳定接口时确定，先用中文说明业务含义。

## 从 V1 和既有讨论继承的已确认事实

1. AgentRig 提供两种使用方式：
   - Codex/Claude Code 通过 MCP 直接控制评测；
   - 用户在 AgentRig Web 中通过自然语言助手管理评测。
2. V1 已实现第一种方式；V2 建设第二种方式。
3. Web 助手是管理评测的主 Agent，不是被测 Agent 的聊天窗口。
4. 主 Agent 后续会调用多个专业子 Agent；AgentTeams 是比赛版本的协作运行时基点。
5. 两种方式必须复用同一套 TestCase、Target、ExecutionProfile、Run、CaseRun、Provider、
   Evaluation 和 Evidence，不建设第二套执行链。
6. V1 已有 Simulation Curator 和 Evidence Judge 两个可选智能组件；V2 可以复用它们，
   但是否以及如何将它们包装为 AgentTeams Agent 仍需逐项确认。
7. Codex/Claude Code 控制的运行不经过 Web 主 Agent；主 Agent 不能在后台扩大外部控制方
   已经确定的测试范围。
8. V1 的原子 MCP 工具继续作为 V2 Agent 调用确定性业务能力的主要边界。
9. 用例与 Sample 的人工审核边界继续保留，Agent 不能自行批准。
10. 真实工具只有在部署允许、执行配置启用且用户明确授权时才能调用。

## 当前实现事实

1. V1 `0.1.0a1` 已完成并通过 AgentScope/Pixcake、Goose/ACP 真实兼容验收。
2. 当前 Web 已有资产、运行和证据管理界面，但没有管理助手对话入口。
3. 当前没有 AgentTeams Adapter、主 Agent 会话、子 Agent Assignment 或协作轨迹。
4. 当前 Simulation Curator 和 Evidence Judge 由执行流程按配置调用，不是 AgentTeams
   中具有独立身份和工作单的 Worker。
5. 当前已有三份 Codex/Claude Code Skill：
   - 构建测试用例；
   - 执行测试用例；
   - 从真实运行证据采集 Sample 草稿。

## 旧 V2 草稿的处理方式

`AgentRig-总体架构-双控制模式与多Agent协作-v0.4.md` 只作为候选设计来源。以下概念不能
直接视为已确认：

- EvaluationJob；
- SelectionPlan / RunSpec 的独立持久化模型；

讨论时优先判断能否复用 V1 已有对象和事件；只有确实解决当前需求时才增加新模型。

## 已确认设计决策

### D1：Web 助手以用户目标为输入，主动查询并在必要时追问

1. 用户可以只用自然语言描述测试目标，不强制先了解 Target、TestCase 或
   ExecutionProfile 等平台对象。
2. 专业用户仍可以在对话中显式指定用例、Target、版本和执行要求。
3. 主 Agent 首先调用平台查询能力，自己查找候选用例、Target、版本、执行方案
   和历史证据，不把可以自行查询的问题退回给用户。
4. 只有当信息缺失会实质改变测试范围、成本、风险或结果解释时，主 Agent 才向
   用户追问。
5. 这是一个类似 Lassist 的持续对话助手，不是把固定表单改写成聊天命令。
6. 执行计划和用例构建过程是一等界面对象，需要可视化展示，不只作为对话文本
   输出。
7. 当前 AgentRig V1 前端是功能性管理界面。V2 会参考并尽量复用 AgentScope
   后续完成的界面优化成果，不在当前阶段重复投入大规模视觉重构。

### D2：助手覆盖完整评测领域，按纵向闭环分步实现

1. Web 助手是评测领域助手，首批理解四类用户意图：
   - 测试：选择用例、形成计划、执行单用例/批量/A-B 并跟踪进度；
   - 构建：创建或修改用例草稿、Fixture 和断言；
   - 诊断：读取运行事件和各评判器结果，解释失败原因；
   - 配置：查询并在权限范围内管理 Target 和 ExecutionProfile。
2. 助手可以使用已有 MCP 能力创建或修改 Target/Profile，但不能修改服务器
   allowlist、注入明文密钥或绕过部署权限。
3. 用例构建产生可视化草稿，继续遵守人工审核边界。
4. 实施不按四类菜单平铺，而按可验收的纵向闭环推进：
   - 第一条闭环：测试 + 诊断；
   - 第二条闭环：构建用例草稿；
   - 配置能力复用已有 MCP，在测试缺少配置或用户明确要求时进入对话。
5. 首个版本不额外建设无边界的“平台管理员 Agent”。

### D3：第一版使用轻量的服务端执行计划草稿

1. V2 第一版新增一个轻量的服务端结构化“执行计划”对象，代码名暂定为
   `EvaluationPlan`，界面对用户统一显示“执行计划”。
2. 执行计划用于保存用户目标、候选用例及选择理由、Target、版本、Profile、执行参数、
   Provider/评判方式、预计 CaseRun 数量、风险提示和校验问题。
3. 执行计划至少支持草稿、已确认、已提交和已取消状态；提交后记录关联的 Run ID。
4. 草稿可以由助手和用户共同编辑。计划确认后冻结；如果还需修改，则基于原计划生成
   新草稿，避免展示内容与实际执行内容不一致。
5. 用户确认时，服务端重新校验资产状态、权限和版本兼容性；校验失败时不创建 Run，
   而是把明确错误反馈到计划中。
6. 计划提交继续调用 V1 的 `run_cases`，实际执行及证据仍以 Run、CaseRun 和对应快照
   为准。执行计划不是第二套执行引擎。
7. 对话消息只负责说明和引用执行计划，不作为计划数据的唯一事实来源。
8. 第一版不引入旧草稿中的 SelectionPlan、RunSpec、EvaluationJob 三层对象，也不建设
   复杂版本历史、审批流、租约或完整任务状态机。

### D4：模型判断业务歧义，代码守住强制安全边界

1. 用户通过自然语言提出需求，因此“用户想做什么”“助手是否补充了重要假设”和“是否
   需要追问”必须由主 Agent 结合完整对话和查询结果判断，不能只依赖固定规则或关键词。
2. 主 Agent 把自然语言理解转成结构化计划，并明确记录用户目标、已确定约束、助手补充
   的假设、资产选择理由和仍未解决的问题，不使用不可解释的单一置信度数值代替说明。
3. 对普通业务范围，主 Agent可以根据语义判断选择：直接执行、展示计划等待确认，或者
   继续追问。无法可靠判断且会实质改变范围、成本、风险或结果解释时，应当追问或确认。
4. 后端策略不负责完整理解自然语言，只负责不可绕过的安全和权限裁决，结果分为允许、
   强制确认和禁止。
5. 真实工具授权、共享资产修改或删除、项目配置的成本/并发/数量上限等由后端强制检查；
   明文密钥、修改服务器 allowlist、Agent 自动审批 Case/Sample 等能力保持禁止。
6. 后端的强制确认或禁止可以覆盖模型的“直接执行”决定；模型不能通过提示词或工具调用
   绕过这些边界。
7. 确认交互优先使用对话中的执行计划卡片或工作区状态，不要求统一使用传统弹窗。

### D5：第一条闭环由一个主 Agent 和两个专业 Agent 组成

1. 新增的 Web 评测助手是 AgentTeams 的主 Agent，是面向用户、理解目标、形成计划、
   调度能力并汇总结果的唯一大脑，不再增加职责重复的 Regression Manager。
2. Simulation Curator 是工具结果模拟领域的专业 Agent，只负责样本查询、理解完整前序
   上下文和生成模拟结果，不负责选择用例或修改用例。
3. Evidence Judge 是证据评判领域的专业 Agent，只负责读取运行证据并产出可独立存档的
   评判结果，不负责运行调度或代替主 Agent 与用户沟通。
4. 主 Agent 可以综合 Rule Judge、Evidence Judge、外部评判和运行事件向用户解释结果，
   但不能覆盖或改写各评判器已经存档的原始输出。
5. Run 调度、并发、超时、事件采集和确定性重试继续由 V1 代码负责，不包装成没有独立
   判断价值的执行 Agent 或监控 Agent。
6. 第一版不新增 Selector Agent、Diagnosis Agent 或 Execution Monitor Agent；先由主
   Agent 调用现有原子能力完成，出现清晰的专业职责和上下文隔离需求后再拆分。
7. 两个专业 Agent 是否参与一次运行，继续由执行计划、Profile、Provider 链和评判配置
   决定，不要求每次运行都调用全部 Agent。

## 当前待讨论

### Q6：主 Agent 会话是常驻进程还是可恢复的回合任务

助手需要支持持续对话、页面刷新、网络断开、长时间 Run 和服务重启。需要确定主 Agent
是否作为长期常驻进程保持内存，还是将会话持久化、把每次用户消息作为可恢复的独立回合
执行。
