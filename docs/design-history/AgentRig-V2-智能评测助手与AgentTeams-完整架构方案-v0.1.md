## 0. 先说结论

AgentRig V2 不重写 V1，也不再建设一套“智能版执行系统”。V2 的核心变化，是在 V1 已经
稳定的评测底座外增加一个用户可直接对话的评测助手，并用 AgentTeams 组织主 Agent 与两个
专业 Agent 的协作。

用户最终有两种使用方式：

1. 在 Codex 或 Claude Code 中，通过 MCP 直接控制 AgentRig；
2. 在 AgentRig Web 中，通过自然语言让平台助手理解需求、制定计划、执行测试和解释结果。

两种方式最终都进入同一条执行链：

```text
TestCase + Target + ExecutionProfile
                    ↓
                  Run
                    ↓
                CaseRun
                    ↓
       Event + Evidence + Evaluation
```

V2 第一版只增加四类必要能力：

- 持续对话和可恢复的助手会话；
- 可查看、可编辑、可确认的执行计划；
- 一个主 Agent 与两个专业 Agent 的 AgentTeams 协作；
- 对计划、执行、证据和协作过程的统一可视化。

它不会增加第二套 Run、第二套 Evidence，也不会引入旧草稿中的多层任务对象和复杂状态机。

## 1. V2 要解决什么问题

### 1.1 V1 已经解决的问题

V1 已经能够让专业用户或外部 Coding Agent：

- 查询和维护测试用例；
- 配置被测 Agent 与执行方案；
- 执行单用例、批量、多版本、重复和 A/B 测试；
- 使用 Fixture、Sample、智能模拟或真实工具结果；
- 保存完整运行事件和评判结果；
- 通过 MCP、HTTP 和 Web 查看与管理资产。

因此，V2 不需要重新设计评测执行能力。

### 1.2 V2 新解决的问题

V1 要求用户理解 TestCase、Target、ExecutionProfile、Provider 和 Evaluator 等平台概念。
V2 要让用户只描述目标，例如：

> “帮我检查 9.3 版本的项目打开功能，上次失败的场景重点跑一下。”

平台助手应当自己：

1. 查询现有用例、Target、版本和历史运行；
2. 识别哪些信息已经明确，哪些信息会影响范围或风险；
3. 必要时向用户追问；
4. 形成可视化执行计划；
5. 调用原有执行能力；
6. 持续跟踪进度；
7. 读取证据并解释通过、失败或无法判断的原因；
8. 在发现覆盖缺口时协助构建新用例草稿。

这不是“给现有表单加一个聊天框”，而是增加一个真正理解评测领域的管理助手。

### 1.3 V2 的用户

- 不熟悉 AgentRig 领域模型，但需要完成 Agent 测试的开发者；
- 希望通过对话执行回归和定位问题的测试人员；
- 需要快速查看测试证据和失败原因的项目负责人；
- 希望让平台自动协助选案，但仍保留人工确认和审核边界的团队；
- 继续使用 Codex/Claude Code，同时希望在 Web 中查看统一结果的专业用户。

## 2. 产品边界

### 2.1 助手负责的四类工作

| 用户意图 | 助手负责什么 | 最终落到哪里 |
|---|---|---|
| 测试 | 选择用例、形成计划、执行单用例/批量/A-B、跟踪进度 | V1 Run / CaseRun |
| 诊断 | 读取事件、规则结果和模型评判，解释失败原因 | V1 Evidence / Evaluation |
| 构建 | 创建或修改用例草稿、Fixture 和断言 | V1 TestCase draft |
| 配置 | 查询并在权限内创建或修改 Target/Profile | V1 Target / ExecutionProfile |

### 2.2 助手不负责什么

V2 主助手不是通用平台管理员，也不是代码修复 Agent。它不能：

- 自动批准 TestCase 或 Sample；
- 修改服务器可执行文件白名单；
- 写入或展示明文密钥；
- 绕过真实工具调用授权；
- 修改已经存档的原始事件和评判结果；
- 替用户发布被测产品；
- 在 Codex/Claude Code 已经控制的一次运行中偷偷扩大范围；
- 直接操纵数据库内部表；
- 把普通调度函数包装成没有独立判断价值的 Agent。

### 2.3 两种控制方式长期并存

V2 上线后，MCP 模式不会被 Web 助手取代。

| 使用方式 | 谁决定测什么 | 是否经过 Web 主 Agent | 适合场景 |
|---|---|---:|---|
| Codex/Claude Code + MCP | 外部 Coding Agent | 否 | 开发过程中结合代码和 diff 做测试 |
| AgentRig Web 助手 | AgentRig 主 Agent | 是 | 用户用自然语言管理评测 |
| 人工/CI + HTTP | 人工或 CI 配置 | 否 | 固定流程、自动化流水线 |

三种入口共享同一套领域服务和数据。入口只决定谁负责理解需求，不决定执行内核如何工作。

## 3. 架构设计原则

### 3.1 智能决策与确定性执行分离

Agent 负责理解、选择、解释和建议；确定性软件负责权限校验、版本展开、并发调度、超时、
事件记录和数据存档。

模型可以建议“跑哪些用例”，但不能自己制造一个未被系统记录的执行过程。

### 3.2 对话不是事实数据库

聊天内容适合表达意图和解释原因，不适合成为执行状态的唯一来源。重要结果必须保存成明确
对象：执行计划、Run、CaseRun、事件和评判记录。

### 3.3 V1 资产继续是唯一事实来源

- TestCase 表示测什么；
- Target 表示测哪个被测 Agent；
- ExecutionProfile 表示怎么测；
- Run/CaseRun 表示实际执行了什么；
- Event/Evaluation 表示发生了什么以及如何评判。

V2 不复制这些对象。

### 3.4 主 Agent 是大脑，专业 Agent 只负责专业判断

主 Agent 理解用户、形成计划并组织工作。Simulation Curator 和 Evidence Judge 只完成
边界清晰的专业任务，不能反过来控制整个评测流程。

### 3.5 默认保持开放，但安全边界由代码兜底

普通业务歧义由模型理解；真实调用、权限、审批、共享资产修改和资源上限由代码强制检查。

### 3.6 先做纵向闭环，再增加 Agent 数量

第一阶段完成“提出目标—计划—执行—诊断”的完整体验。只有出现独立专业知识、不同工具权限
或明显上下文隔离需求时，才新增子 Agent。

                │                       │
                ▼                       │
┌───────────────────────────────────┐   │
│       V2 智能助手应用层            │   │
│ 会话 │ 意图理解 │ 上下文查询        │   │

┌───────────────────────────────────┐   │
│       AgentTeams 协作层            │   │

│ ├─ Simulation Curator             │   │
│ └─ Evidence Judge                 │   │
└───────────────┬───────────────────┘   │
                │ 原子业务能力          │
                └───────────┬───────────┘
                            ▼

- 会话、计划、运行和协作轨迹持久化；
- 日志、指标、Trace 和审计。

## 5. 三个 Agent 的职责

### 5.1 主 Agent：评测助手

这是唯一直接面向用户的 Agent，也是整个团队的大脑。

它负责：

- 理解当前对话中的测试目标；
- 主动查询用例、Target、Profile、版本和历史结果；
- 判断是否需要追问；
- 形成、修改和解释执行计划；
- 决定本次计划是否需要智能模拟和证据评判；
- 提交 Run 并跟踪状态；
- 读取各评判器结果和原始证据；
- 向用户解释结论和下一步建议；
- 在需要时创建用例或配置草稿。

它不直接执行 CaseRun 的状态机，也不自己模拟工具结果。

### 5.2 专业 Agent：Simulation Curator

它解决“被测 Agent 调用了工具，但测试环境需要提供一个可信结果”的问题。

它只接收与当前工具调用有关的上下文：

- 工具名称、参数和输出约束；
- 用例的模拟说明和初始状态；
- 当前 CaseRun 到此为止的完整脱敏上下文；
- 当前模拟状态和之前生成的相关结果；
- 样本查询结果和校验反馈。

它输出结构化工具结果和必要的状态变化，之后仍由 V1 Validator 校验。它不能修改用例、
断言或评测标准。

### 5.3 专业 Agent：Evidence Judge

它解决“规则无法完全表达语义目标，需要根据真实执行证据判断”的问题。

它读取：

- 用例的评判要求；
- Rule Judge 已经产生的确定性结果；
- CaseRun 的脱敏事件；
- 可以合法引用的 Evidence ID。

它输出通过、失败或无法判断，并说明每条标准的判断和证据引用。输出独立存档，不能覆盖
Rule Judge 或外部控制方的评判。

### 5.4 哪些组件不是 Agent

以下工作没有独立语义判断价值，继续使用确定性代码：

- 用例与版本组合展开；
- 并发队列和超时；
- Driver 请求与 Session 管理；
- Provider 顺序降级；
- Schema 校验；
- Rule 断言；
- 事件脱敏与落库；
- 权限和确认策略；
- Run 取消和服务重启后的中断处理。

第一版不增加 Selector Agent、Execution Monitor Agent 或 Diagnosis Agent。主 Agent 使用
现有原子能力足以完成这些工作。

## 6. 智能助手应用层的模块设计

### 6.1 对话会话模块

负责保存一段连续对话以及它关联的计划、Run 和上下文。用户刷新页面、切换设备或服务重启
后，仍能回到同一段工作中。

它保存的不是一个永远驻留内存的 Agent，而是可恢复的会话记录。

### 6.2 Agent 回合模块

用户每发一条消息、确认一个计划，或者一个长时间 Run 结束，都会产生一次新的 Agent 回合。

每个回合负责：

- 恢复本次所需上下文；
- 调用模型和工具；
- 持续保存输出事件；
- 支持取消、失败和重试；
- 防止网络重试造成重复提交 Run。

回合结束后不要求 Agent 进程继续常驻。连续体验由持久化会话保证。

### 6.3 意图理解与追问模块

模型结合完整对话，把自然语言整理成以下信息：

- 用户最终想验证什么；
- 用户明确指定了哪些条件；
- 助手为了完成任务补充了哪些假设；
- 当前还缺少哪些会影响范围、成本、风险或结果解释的信息。

助手应先查询，再追问。能够从平台找到的信息，不应重新要求用户提供。

### 6.4 上下文查询模块

主 Agent 通过原子 MCP 能力按需读取：

- 用例与能力标签；
- Target、版本和连通性；
- ExecutionProfile；
- 历史 Run、CaseRun、事件和评判；
- Sample 与 Fixture 的可用情况；
- 创建或执行相关的 Schema。

该模块不一次性把整个数据库塞入模型，而是根据当前问题逐步查询并返回紧凑结果。

### 6.5 执行计划模块

执行计划是 V2 新增的核心结构化对象。它用于回答三个问题：

1. 用户希望验证什么；
2. 助手准备实际执行什么；
3. 为什么这样选择。

计划中包含：

- 用户目标和助手摘要；
- 选中的用例及选择理由；
- Target、版本和执行 Profile；
- 单次、批量或 A/B 方式；
- 并发、重复次数等执行参数；
- Provider 和评判方式；
- 预计展开的 CaseRun 数量；
- 已知风险、兼容性问题和待确认事项。

计划不是 Run。计划说明“准备执行什么”，Run 记录“实际执行了什么”。

### 6.6 确认与安全策略模块

该模块采用两层判断：

第一层由模型负责业务语义：

- 需求是否已经足够明确；
- 助手的选择是否需要向用户解释；
- 是否应当继续追问或展示计划确认。

第二层由代码负责强制边界：

- 当前用户是否有权限；
- 是否涉及真实工具；
- 是否修改或删除共享资产；
- 是否超过项目设置的数量、并发或成本边界；
- 是否属于 Agent 永远不能执行的动作。

后端可以覆盖模型的“直接执行”决定，模型不能绕过后端策略。

### 6.7 运行编排模块

主 Agent 确认计划后，通过现有原子能力调用 V1 `run_cases`。该模块负责：

- 在提交前重新校验计划引用的资产；
- 防止重复提交；
- 保存计划与 Run 的关联；
- 把 Run 状态变化转成用户可理解的进度；
- 在 Run 结束后触发新的助手回合进行汇总。

它不复制 V1 Planner 或 Scheduler。

### 6.8 结果解释模块

主 Agent 根据问题选择性读取：

- Run 汇总；
- CaseRun 状态和跳过原因；
- Driver request/session 证据；
- assistant、tool call、provider 和 tool result 时间线；
- Rule、Evidence Judge 和外部评判；
- 错误类型、重试信息和资源使用。

它负责把证据组织成解释，但不能改写原始结果。用户始终可以从解释跳转到对应证据。

### 6.9 用例构建模块

当用户要求创建用例，或测试过程中发现覆盖缺口时，助手可以生成用例草稿：

- 帮助整理用户输入轮次；
- 选择能力标签和支持版本；
- 构建 Fixture；
- 编写结构化断言和语义评判要求；
- 展示每一部分的来源和修改结果。

草稿需要在结构化编辑界面中可视化。助手只能创建和修改允许修改的状态，人工审核边界保持
不变。

### 6.10 配置辅助模块

助手可以查询、创建和修改 Target/Profile，但配置仍是独立资产，不隐藏在对话内部。

配置辅助重点解决：

- 根据 Driver 能力解释需要哪些配置；
- 检查 Target 连通性；
- 说明版本覆盖和继承结果；
- 帮助生成新的 Profile；
- 在执行前发现 Provider、评判器和工具模式不兼容。

它不能控制部署白名单，也不能接触真实 Secret 值。

## 7. 执行计划的生命周期

第一版计划只有四个用户可理解的状态：

```text
草稿 ──确认──→ 已确认 ──提交──→ 已提交
  │                │
  └────取消────────┴──────────→ 已取消
```

### 7.1 草稿

助手和用户都可以修改。前端应明确显示哪些内容来自用户、哪些是平台默认、哪些是助手选择及
其理由。

### 7.2 已确认

计划内容被冻结。用户的明确自然语言指令可以被主 Agent 视为业务确认，但真实工具、权限、
共享资产修改和资源上限仍受后端强制确认策略约束。

### 7.3 已提交

计划已经产生 Run，并记录 Run ID。此后实际执行内容以 Run/CaseRun 快照为准。

### 7.4 已取消

计划不再提交。取消计划和取消已经存在的 Run 是两个不同动作。

### 7.5 修改已确认计划

已确认或已提交的计划不原地修改。需要调整时，以原计划为基础创建新草稿。这样可以确保
用户当时看到的内容和实际执行内容一致。

第一版不增加计划审批流、复杂版本树或独立 EvaluationJob。

## 8. AgentTeams 如何进入现有执行链

### 8.1 AgentTeams 的位置

AgentTeams 是 V2 的多 Agent 协作层，负责：

- 表达主 Agent 与专业 Agent 的身份；
- 把专业任务分派给对应 Worker；
- 传递必要上下文或上下文引用；
- 保存协作过程、状态和输出；
- 支持人类查看和介入；
- 把团队执行与 AgentRig 的计划、Run、CaseRun 关联。

AgentTeams 不替代 AgentRig 的评测内核。AgentTeams 管“谁来判断”，AgentRig Core 管“如何
安全、可重复地执行并存证”。

### 8.2 两层调度

系统中存在两种含义不同的调度：

1. 主 Agent 的语义调度：决定测试目标、计划和需要哪些专业能力；
2. V1 内核的确定性调度：展开 CaseRun、控制并发、超时和执行顺序。

主 Agent 是大脑，但不需要亲自管理线程、队列和每个 Driver 事件。

### 8.3 Simulation Curator 的触发

主 Agent 在执行计划中选择允许使用智能模拟的 Profile。运行时只有当 Provider Chain 到达
Simulation Curator 时，V1 才发出一项专业模拟任务，由 AgentTeams 交给 Curator Worker。

因此，主 Agent 决定是否启用该能力，V1 决定在哪个准确工具调用点触发，AgentTeams 负责
把任务交给正确身份的 Worker。

### 8.4 Evidence Judge 的触发

主 Agent 在计划中选择 Evidence Judge 作为评判能力。CaseRun 执行结束、证据完整落库后，
V1 发出证据评判任务，由 AgentTeams 交给 Judge Worker。评判结果回到 V1 Evaluation 存档。

### 8.5 上下文传递原则

Agent 之间不复制整份数据库或无上限聊天历史。每项专业任务只包含：

- 任务目标；
- 必要的结构化输入；
- 计划、Run、CaseRun 或 Evidence 引用；
- 安全脱敏后的上下文；
- 输出格式和失败处理要求。

大体积事件通过引用按需读取，小结果可以直接传递。

### 8.6 协作失败如何处理

- Curator 不可用时，Provider Chain 按 Profile 继续尝试下一个 Provider；没有可用 Provider
  时，该工具调用按现有规则失败。
- Evidence Judge 不可用时，保存独立的评判错误，不把它伪装成 Agent 行为失败。
- 主 Agent 不自动扩大执行范围重跑；是否重跑由用户要求或后续明确策略决定。
- AgentTeams 故障不能损坏已经保存的 V1 Run、事件和确定性评判。

## 9. 状态与数据归属

### 9.1 V1 对象保持不变

V2 继续使用 TestCase、Target、ExecutionProfile、Sample、Run、CaseRun、RunEvent 和
Evaluation。它们的业务含义不因 Web 助手而改变。

### 9.2 V2 新增的最小状态

| 状态 | 解决的问题 | 是否替代 V1 对象 |
|---|---|---:|
| 助手会话 | 保存连续对话及其关联工作 | 否 |
| 对话事件 | 保存消息、计划卡片、确认和系统通知 | 否 |
| Agent 回合 | 保存一次可取消、可恢复的推理过程 | 否 |
| 执行计划 | 保存准备执行的范围、理由和确认状态 | 否 |

第一版不单独建设 EvaluationJob、RunSpec、SelectionPlan、Assignment、Artifact Store 和
GateRecommendation 等对象。

### 9.3 各类事实由谁负责

| 用户想知道的问题 | 权威来源 |
|---|---|
| 用户说了什么 | 对话事件 |
| 助手准备测什么 | 执行计划 |
| 实际执行了什么 | Run / CaseRun 快照 |
| 运行中发生了什么 | RunEvent / Evidence |
| 各评判器怎么判断 | Evaluation |
| 哪个 Agent 完成了哪项专业工作 | AgentTeams 协作轨迹及关联引用 |

这样可以避免聊天文本、AgentTeams 消息和 AgentRig 数据库各自保存一套互相矛盾的结论。

## 10. 异步执行、断线恢复与取消

### 10.1 不使用长期常驻 Agent 进程

主 Agent 采用“持久会话 + 独立回合”的方式运行。每次用户消息或系统事件触发一个回合；
回合结束后释放模型调用资源。

### 10.2 Run 与聊天连接解耦

提交 Run 后：

- 用户关闭页面，Run 继续执行；
- WebSocket/SSE 断开不影响 Run；
- 页面重新连接后从持久化事件游标继续读取；
- Run 到达终态后触发一个系统事件；
- 主 Agent 在新回合中读取结果并生成总结。

实时通道只负责及时展示，不负责保存状态。

### 10.3 三种取消要分开

| 用户动作 | 取消什么 | 不影响什么 |
|---|---|---|
| 停止生成 | 当前 Agent 回合 | 已提交 Run |
| 取消计划 | 尚未提交的计划 | 已存在 Run |
| 取消运行 | Run 中尚未完成的 CaseRun | 对话历史和已完成证据 |

### 10.4 重试与幂等

用户重发消息、浏览器重连或后台任务恢复时，不能重复创建计划或 Run。每个有副作用的动作都
应与当前回合和计划关联，并能识别已经成功完成的同一动作。

## 11. 前端信息架构

V2 前端不是单独的聊天室，而是“对话 + 结构化工作区”。

### 11.1 推荐布局

```text
┌────────────┬──────────────────────────┬──────────────────────┐
│ 会话列表   │ 对话区                   │ 当前工作区           │
│            │ 用户与主 Agent 对话      │ 执行计划             │
│ 历史会话   │ 查询/工具/协作状态       │ 用例草稿             │
│ 收藏任务   │ 确认卡片与系统通知       │ Run 进度与证据        │
└────────────┴──────────────────────────┴──────────────────────┘
```

桌面端可以采用三栏，窄屏可以将工作区变为可切换面板。具体视觉样式以后跟随 AgentScope 的
界面优化成果。

### 11.2 执行计划视图

需要清楚展示：

- 用户目标；
- 选中的用例和理由；
- Target、版本和 Profile；
- 展开后的预计执行数量；
- 模拟和评判配置；
- 助手补充的假设；
- 风险、错误和待确认项；
- 修改、确认、取消和查看 Run 的动作。

### 11.3 用例构建视图

用例不应只显示一大段 JSON。需要按业务结构展示：

- 基本信息与标签；
- 支持版本；
- 用户轮次；
- 每轮 Fixture 和模拟说明；
- 断言与语义评判要求；
- 草稿与人工审核状态。

助手在对话中做出的修改必须立即反映到结构化草稿；用户在界面中的编辑也必须进入助手的
后续上下文，不能形成两份状态。

### 11.4 Run 与证据视图

需要同时展示：

- 父 Run 的调度状态和数量汇总；
- 每个 CaseRun 的版本、状态和评判；
- skipped 的明确原因；
- Driver request/session 关联；
- assistant 文本、工具调用、Provider、工具结果和最终消息时间线；
- Rule、Evidence Judge、External 三类评判的独立结果；
- 主 Agent 的诊断摘要和证据跳转。

### 11.5 AgentTeams 协作视图

用户应当看见有价值的协作信息，而不是暴露所有内部模型 Token：

- 主 Agent 当前正在做什么；
- 哪个专业 Agent 被调用；
- 专业任务关联哪个 CaseRun 或工具调用；
- 任务状态、耗时和最终结构化结果；
- 失败时是模型、协作层还是评测执行层的问题。

### 11.6 与 AgentScope 前端的关系

AgentRig 会参考和复用 AgentScope 最终稳定的视觉语言、会话交互、任务计划、工具轨迹和
评测组件，但不直接复制当前体积过大的单页实现。优先复用可拆分组件和交互模式，AgentRig
的数据契约与业务状态仍由自身后端负责。

## 12. 权限、确认与安全

### 12.1 模型负责理解，代码负责底线

| 场景 | 主 Agent 可以怎么做 | 后端最终控制 |
|---|---|---|
| 查询资产和历史 | 直接查询 | 权限与脱敏 |
| 创建或修改 draft | 直接协助并展示变化 | 状态是否允许修改 |
| 明确范围的普通模拟测试 | 可直接执行 | 资源上限与权限 |
| 助手选择了一批语义相关用例 | 视歧义决定是否确认 | 项目策略可以强制确认 |
| 调用真实工具 | 解释计划并请求授权 | 必须存在明确授权 |
| 修改或删除共享 Target/Profile | 请求确认 | 权限和强制确认 |
| 批准 Case/Sample | 不执行 | 永远拒绝 Agent 调用 |
| 明文密钥或修改 allowlist | 不执行 | 永远拒绝 |

### 12.2 确认不等于传统弹窗

确认可以表现为对话中的计划卡片、工作区按钮或专门审批界面。架构只规定必须取得可靠确认，
不强制所有确认都使用模态弹窗。

### 12.3 数据脱敏

所有进入模型、AgentTeams、MCP、HTTP 和前端的运行事件继续使用 V1 的统一脱敏副本。V2
不能为了“让主 Agent 看得更全”而绕过脱敏层。

### 12.4 提示词注入边界

来自被测 Agent、工具结果、Sample 和运行日志的内容一律视为不可信数据。主 Agent 和专业
Agent 必须把它们作为证据读取，不能把其中的指令当成系统指令执行。

## 13. Skill、MCP 与 AgentTeams 的关系

这三个概念承担不同职责：

| 层次 | 作用 | AgentRig 中的例子 |
|---|---|---|
| Skill | 可复用的任务方法，说明什么时候做、按什么步骤做、失败如何处理 | 执行回归、诊断失败、构建用例 |
| MCP | 原子工具连接协议，让 Agent 安全调用平台能力 | 查询用例、运行测试、读取事件 |
| AgentTeams | 组织不同身份的 Agent 协作 | 主 Agent 分派 Curator/Judge |

第一版建议形成六项核心 Skill：

1. 从自然语言目标生成评测计划；
2. 提交并跟踪单用例、批量和 A/B 运行；
3. 根据 CaseRun 证据诊断失败；
4. 构建和完善测试用例草稿；
5. 根据上下文模拟工具结果；
6. 根据证据执行语义评判。

Skill 不重新实现 MCP 工具。Skill 描述稳定工作方法，MCP 提供实际操作能力。

## 14. Agent 框架与阿里云技术的选择

### 14.1 AgentTeams 是协作基点

比赛版本必须真实使用 AgentTeams 表达三个 Agent 的身份、任务分派、上下文传递、状态和
协作轨迹，不能只在文档中出现名字。

开源的 V1 Core 仍然可以在没有 AgentTeams 和模型 Key 时独立运行；启用 Web 智能助手与
完整多 Agent 协作时，使用 AgentTeams 运行配置。

### 14.2 Agno 的定位

Agno 可以作为单个 Agent 的模型循环或会话 Runtime 候选，但第一版不引入完整 AgentOS，
也不使用 Agno Team 替代 AgentTeams。

原因是 AgentOS 的 Session、Run、审批、Trace 和 Eval 与 AgentRig 已有能力重叠，整套引入
会形成两套事实来源。架构保留一个薄的 Agent Runtime 适配边界；确有收益时，可以在不改变
AgentTeams 和 AgentRig Core 的前提下接入 Agno。

### 14.3 阿里云产品不是整套强制绑定

比赛要求的重点是 AgentTeams 和 Skill。其他阿里云产品以必要性和真实价值为准，不按数量
堆叠。

比赛版本应接入至少一个有实际用途的阿里云官方 Skill，以规避赛题正文和 FAQ 对“推荐/必须”
表述不一致的风险。优先候选是：

- 查询 SLS 日志并作为失败诊断的补充证据；
- 将评测报告和证据包归档到 OSS。

最终只选择真正进入端到端 Demo 的能力，并说明不用它时的替代接口和迁移成本。

## 15. 可观测与审计

V2 需要建立一条可追踪关联链：

```text
助手会话
  → Agent 回合
    → 执行计划
      → AgentTeams 专业任务
        → Run
          → CaseRun
            → Event / Evaluation
```

每层关注点不同：

- 会话层：用户目标、追问、确认和取消；
- Agent 回合层：模型调用、工具调用、耗时、Token 和错误；
- 协作层：谁分派给谁、输入引用、状态和结果；
- 运行层：Driver、工具、Provider、评判和资源耗时；
- 审计层：权限判断、真实工具授权、共享资产变化和人工审核。

前端可以按用户需要逐层展开，默认不展示冗长的原始模型内容。

### 15.1 错误归属必须清楚

系统至少要区分：

- 用户输入或配置问题；
- 主 Agent 理解或工具调用问题；
- AgentTeams 分派或 Worker 问题；
- 模型 Provider 问题；
- Target/Driver/被测 Agent 问题；
- 工具结果 Provider 问题；
- 评判器错误；
- 平台内部错误。

不同错误不能统一显示成“测试失败”。

## 16. 关键用户流程

### 16.1 明确执行一个用例

用户说“在 target_lassist_local 上跑 099”。主 Agent 查询 Target 和用例，按平台默认规则
展开用例支持版本，生成并提交计划。用户可以立即看到计划、Run 进度和最终证据。

如果未涉及强制确认项，明确的原始指令可以作为业务授权，不必机械地重复确认。

### 16.2 按自然语言目标选择一批用例

用户说“测试项目打开相关能力”。主 Agent 查询能力标签、工具关联和历史失败，得到候选用例，
说明选择理由与覆盖缺口。若选择结果存在重要假设，先展示计划让用户确认，再提交 Run。

### 16.3 自动等待并诊断失败

Run 提交后异步执行。结束时产生系统事件并触发新回合。主 Agent读取失败 CaseRun、规则结果、
Evidence Judge 结果和关键事件，向用户说明：失败发生在哪一层、证据是什么、是否属于用例
问题、被测 Agent 问题或平台问题。

### 16.4 从失败构建用例草稿

用户要求“把这次失败保留成用例”。主 Agent 读取现有证据，生成草稿轮次、Fixture、断言和
标签，在结构化构建界面中展示。用户修改后仍保持 draft，之后由人工审核。

### 16.5 配置缺失时协助处理

如果用户指定的 Target 不存在或 Profile 不兼容，助手先解释缺少什么，再根据权限创建草稿
或引导用户完成必要配置。它不会在后台使用未经授权的真实工具或 Secret。

## 17. 分阶段实施

### 阶段一：测试与诊断闭环

交付目标：用户能在 Web 中通过自然语言完成一次真实测试并理解结果。

范围：

- 助手会话与 Agent 回合；
- 意图理解、主动查询和追问；
- 执行计划及计划卡片；
- AgentTeams 主 Agent、Curator、Judge 身份与协作；
- 调用 V1 Run；
- 运行进度、结果摘要和证据跳转；
- 强制安全策略、断线恢复和取消。

### 阶段二：用例构建闭环

交付目标：用户能通过对话和结构化界面共同构建可审核的用例草稿。

范围：

- 多轮输入编辑；
- Fixture 和断言可视化；
- 从运行证据生成草稿；
- 标签、版本和评判要求辅助；
- 人工审核入口衔接。

### 阶段三：配置辅助闭环

交付目标：助手可以在权限范围内帮助用户准备 Target/Profile，并在运行前解释兼容性问题。

范围：

- Target/Profile 查询与草稿；
- Driver 能力解释；
- 连通性和版本覆盖检查；
- Provider 与 Evaluator 配置建议；
- 共享配置修改确认。

### 阶段四：比赛与产品化完善

范围：

- AgentTeams 可视化协作证据；
- 一个有真实价值的阿里云官方 Skill；
- 完整 Demo、失败分支和恢复演示；
- 部署说明、样例数据和可复现实验；
- 可观测指标和演示视频；
- 参考 AgentScope 最终设计完成界面统一。

---

## 18. 第一阶段验收标准

第一阶段完成时，至少满足以下条件：

1. 用户只描述测试目标，主 Agent 能主动查询资产，不要求用户先理解平台模型。
2. 需求不明确时会追问；需求明确时不会机械重复确认。
3. 执行前可以看到结构化计划、选择理由、版本和预计 CaseRun 数量。
4. 计划确认后仍通过 V1 `run_cases` 执行，没有第二条执行链。
5. 单用例、批量、多版本和 A/B 至少各有可复现流程。
6. 页面断开后 Run 继续，重连后可以恢复计划、进度和结果。
7. Simulation Curator 和 Evidence Judge 以不同身份通过 AgentTeams 留下协作轨迹。
8. 未启用某个专业 Agent 时，运行仍按 Profile 正常完成。
9. 主 Agent 的诊断能够引用真实 CaseRun 事件和各评判器结果。
10. Rule、Judge 和 External 评判在界面中保持独立，主 Agent 不覆盖原始结论。
11. 真实工具、共享配置和审核边界不能被提示词绕过。
12. Codex/Claude Code MCP 模式继续通过现有回归测试，不依赖 Web 主 Agent。
13. AgentTeams 或模型服务故障不会破坏已落库的 Run 和 Evidence。
14. 至少完成 AgentScope/Pixcake 与 Goose/ACP 两种被测 Agent 的端到端复验。

---

## 19. 明确不在 V2 第一版建设的内容

- 第二套评测任务或执行引擎；
- 独立的 EvaluationJob、RunSpec、SelectionPlan 三层模型；
- 通用 Assignment Scheduler、租约和心跳系统；
- 通用 Agent Capability Registry；
- 独立 Artifact Store；
- 自动发布 Gate；
- 自动修复被测 Agent 代码；
- Agent 自动批准 Case/Sample；
- 为比赛数量新增无价值 Agent；
- 整套引入 Agno AgentOS；
- 大规模重写当前前端后再开始业务闭环。

这些能力只有在真实场景证明现有对象无法承载时，才重新进入设计讨论。

---

## 20. 开工前还需最后确认的事项

本方案已经给出完整模块边界，但以下实现选择应在开工前通过小规模验证确认：

1. AgentTeams 采用的稳定版本、Manager/Worker Runtime 和自定义 Web 接入方式；
2. AgentTeams 协作轨迹与 AgentRig 会话/Run 的关联方式；
3. 主 Agent 默认模型以及用户自带模型配置方式；
4. V2 第一阶段是否直接使用 AgentTeams 的会话存储，还是只保存映射并以 AgentRig 会话为主；
5. 比赛 Demo 最终选择 SLS 日志查询还是 OSS 报告归档 Skill；
6. AgentScope 新界面中哪些组件可稳定复用。

这些问题影响技术选型和实施工作量，但不改变本文确定的产品边界和总体架构。

## 21. 最终架构判断

AgentRig V2 的价值不在于增加更多 Agent，而在于把三种能力真正闭环：
