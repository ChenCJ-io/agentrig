## 0. 决策摘要

AgentRig 不转型为通用 Agent Framework，也不复制完整的 Agent 可观测平台。下一阶段产品定位是：

> 面向 Agent 运行时的证据优先验证与发布控制面，把生产失败转化为经过审核、可以重放、能够阻断
> 回归发布的测试资产。

核心闭环为：

```text
生产 Agent / AgentScope / 其他 Runtime
              │ OTLP、AG-UI、Native Driver
              ▼
ProductionSession / Trace / Span
              │ 脱敏、人工标注、自动评分
              ▼
Failure Pattern / Reviewed Evidence
              │ 带来源关系生成草稿
              ▼
TestCase / SuiteVersion
              │ Run / A-B
              ▼
QualityReport / ComparisonReport / ReleaseGate
              │ 发布后观察
              └──────────────────────► 复发监控
```

实施顺序固定为：

1. 收口 V2.2 的报告、门禁、真实 E2E 和 Skill 契约。
2. 保留 AgentTeams v1.1.2 历史证据，增加 v1.2.2 当前基线。
3. 接入 AgentScope 2.0/AG-UI，扩展运行时证据语义。
4. 冻结 Target Capability Snapshot，并上线 AgentScope 专项回归套件。
5. 引入独立的生产证据域，形成 Trace 到 Case 草稿的有审阅链路。
6. 在真实数据基础上建设 Judge 对齐、Failure Signal 和复发监控。
7. 最后补齐多项目、耐久调度、RBAC 和规模化部署。

## 1. 背景与外部变化

### 1.1 Latitude 带来的产品启示

Latitude 当前主线已经形成“观察、理解、修复、验证”的生产反馈闭环，重点包括 OTLP Trace、人工
标注、行为/失败模式、评测对齐、生产数据集、回放实验和复发监控。AgentRig 应吸收这条闭环，但不
复制它的 Prompt IDE、模型网关和重型数据基础设施。

对 AgentRig 最有价值的启示是：回归用例不能永远只靠人工预先设计，生产中已经发生且经确认的失败
应当成为带 provenance 的测试资产。

### 1.2 AgentScope 2.0 带来的协议变化

AgentScope 2.0 的统一事件流、细粒度权限、暂停恢复、Middleware、长期记忆、隔离 Workspace、Agent
Service 和 Agent Teams 扩大了被测系统的状态空间。现有 AgentRig Driver 主要记录消息、工具调用、
usage 和终态，无法完整表达：

- 权限请求与授权结果；
- interrupt、resume 和等待外部执行；
- 模型调用边界与缓存 token；
- 父子 Agent、委派来源和嵌套执行；
- Memory read/write 与 Workspace artifact；
- 多模态数据和结构化结束原因。

### 1.3 AgentTeams v1.2.x 带来的交付变化

AgentRig 当前竞争环境固定为 AgentTeams v1.1.2。v1.2.x 改为新的资源命名和 Worker 组织方式，并
引入 QwenPaw 统一 Runtime、原子任务交接、Skill 分发及热加载。升级后，“资源已创建”不再足以证明
运行内容一致，还要验证 Skill 内容哈希、分配关系、启用状态和房间成员收敛。

## 2. 当前基线与差距

### 2.1 必须继续保留的优势

- `Run → CaseRun → RunEvent/Evaluation` 是测试执行的不可变事实链。
- Simulation Curator 只生成工具结果，Evidence Judge 只评判证据，职责不可合并。
- Fixture → Sample → Curator → Real Tool 的 Provider Chain 保持不变。
- Core 决定权限、确认、幂等和状态机；模型只能提出动作。
- 基础设施故障与产品失败分开，`inconclusive` 不能算作 pass。
- OpenTelemetry、搜索索引和通知系统都是投影，不得反向改写业务事实。

### 2.2 当前主要缺口

| 缺口 | 当前状态 | 目标状态 |
|---|---|---|
| 质量汇总 | QualityReport v1、API/CLI、来源哈希和冻结价格快照已实现 | 外部 live 指标按目标环境归档 |
| A/B 门禁 | ComparisonReport、Policy/Gate、CLI 和 Reference 负向控制已实现 | 增加 Capability 可比性、GitHub Check 和 Web |
| Runtime 事件 | 扁平 DriverEvent | 权限、恢复、嵌套 Agent、Memory、Workspace 可表达 |
| 环境复现 | 冻结 Target/Profile | 运行时、模型、Tool、Skill、权限和镜像可哈希 |
| AgentTeams | 固定 v1.1.2 | 历史基线保留，v1.2.2 并行验收 |
| 测试来源 | 人工 Case/Sample 为主 | 生产 Trace 经审核转为 Case/Suite |
| Judge 可信度 | 单次 Evaluation | 人工标签、版本快照、对齐报告和漂移 |
| 失败治理 | Run 级查看 | Pattern 生命周期、复发和发布关联 |
| 生产基础 | 单工作区、进程内调度 | Project 隔离和 PostgreSQL 耐久 lease |

## 3. 产品边界

### 3.1 AgentRig 负责

- 接入不同 Agent Runtime 并规范化可公开证据；
- 冻结被测能力和执行环境；
- 设计、执行、评判和重放测试；
- 比较版本，生成可审计发布门禁；
- 接收经脱敏的生产轨迹，支持人工复核和测试资产沉淀；
- 跟踪已确认失败是否修复、是否复发。

### 3.2 AgentRig 不负责

- 提供业务 Agent 的 Memory、RAG、规划器或模型路由；
- 代替 AgentScope/AgentTeams 编排和运行 Agent；
- 保存或展示模型隐藏思维过程；
- 自动批准真实工具、生产写操作或外部代码修改；
- 在没有证据和审批时自动生成并激活 Judge；
- 在规模需求未出现前引入 ClickHouse、Temporal、Kafka 等基础设施。

## 4. 目标架构与事实域

```text
┌────────────────────── Runtime / Production Plane ──────────────────────┐
│ AgentScope Service │ AgentTeams/QwenPaw │ AG-UI Agent │ Other Targets │
└───────────┬───────────────────┬────────────────┬───────────────────────┘
            │ Driver/AG-UI      │ Matrix/Skills  │ OTLP
            ▼                   ▼                ▼
┌──────────────────────── AgentRig Integration Plane ────────────────────┐
│ Driver Registry │ Event Normalizer │ Capability Collector │ OTLP Ingest│
└──────────────────────────────┬──────────────────────────────────────────┘
                               ▼
┌──────────────────────────── AgentRig Core ──────────────────────────────┐
│ Test Domain                 │ Production Evidence Domain               │
│ Run/CaseRun/RunEvent        │ Session/Trace/Span                       │
│ Evaluation/Decision         │ Annotation/Score/FailurePattern          │
│ Quality/Comparison/Gate     │ Trace→Case Draft Lineage                 │
│                             │                                          │
│ Shared: Project / Redaction / Identity / Audit / Retention / Hashing   │
└──────────────────────────────┬──────────────────────────────────────────┘
                               ▼
┌────────────────────────── Product / Delivery ───────────────────────────┐
│ Web Review │ CLI/GitHub Gate │ Reports │ Alerts │ Evidence Bundle      │
└──────────────────────────────────────────────────────────────────────────┘
```

### 4.1 测试事实域

现有 Run、CaseRun、RunEvent、Evaluation、DecisionRecord 和 AgentInvocation 继续作为测试事实。报告和
Gate 从这些事实派生，不建立第二套“质量运行”。

### 4.2 生产证据域

生产 Session/Trace/Span 是被观察事实，可能被采样、迟到或部分缺失。它们不得直接改变 Run 状态，也
不得在未审核时成为 approved TestCase。所有 Trace→Case 转换必须保存来源和审核人。

### 4.3 共享边界

Project、脱敏策略、身份、保留策略和 canonical hash 可被两个事实域共享。Project 最小边界必须早于
生产 ingest 对外开放，否则无法可靠实施数据隔离、保留和访问控制。

## 5. 优化专题与依赖

| 专题 | 主要产物 | 前置 | 阻断条件 |
|---|---|---|---|
| V2.2 收口 | Quality/Comparison/Gate、真实 E2E、Skill contract | 现有事实链 | 报告不可重放或 E2E 仍全 Mock |
| AgentTeams 双基线 | v1.1.2 archive、v1.2.2 profile、compat report | 固定版本和 live 环境 | 旧证据被覆盖或新 Skill 不可验证 |
| AgentScope Driver | Event v2、AG-UI/native adapter、session state machine | Driver v1 | 权限/恢复事件丢失 |
| Capability Snapshot | Snapshot schema/hash/drift verdict | Driver probe | Secret 进入快照或 A/B 环境不可比 |
| 专项回归套件 | 权限、记忆、沙箱、恢复等 Suite | Driver + Snapshot | capability 缺失被误报为 pass |
| OTLP 生产接入 | Trace 模型、ingest、Trace→Case draft | Project-lite | PII 策略、配额或保留策略缺失 |
| Judge 对齐 | Annotation、EvaluatorVersion、AlignmentReport | 可审核证据 | Judge 被静默自动修改 |
| Failure Signal | Pattern、状态机、复发和通知 | 足够标签/评分数据 | 聚类结果被当作已确认事实 |
| Product 基础 | Project、lease scheduler、RBAC 路线 | PostgreSQL | SQLite 被错误宣传为多副本安全 |

## 6. 统一设计原则

### 6.1 不可变与版本化

- 所有 CaseRun 冻结 Target/Profile/Capability 快照。
- Evaluator、ReleasePolicy、Skill、价格和测试套件都以版本或内容哈希引用。
- 报告必须包含 `source_snapshot_hash`，相同输入得到相同结果。
- 历史结果不随当前配置变化重新解释；重算生成新报告版本。

### 6.2 权限与人工边界

- Target 内部的权限事件是被测证据，不给 AgentRig 自身授权。
- Trace→Case 只能创建 draft；发布 Case/Sample、激活 Judge、修改 Gate、调用真实工具仍需既有审批。
- Failure Pattern 自动发现只产生 candidate，人工确认后才进入阻断策略或外部通知。

### 6.3 缺失和不确定性

- `unknown`、`unsupported`、`not_observed` 和 `not_applicable` 必须区分。
- 缺失 usage 不填零；成本无法可靠计算时返回 `null`。
- 基础设施、遥测缺失和 Runtime 不支持不得自动记为产品 fail。
- 门禁输入不完整时返回 `inconclusive`，CI 不得把它视为成功。

### 6.4 渐进基础设施

V2.3/V2.4 使用 PostgreSQL、现有 FastAPI 和有界后台任务完成首版。只有当写入量、查询延迟或恢复
目标达到已记录阈值时，才评审 ClickHouse、消息队列或工作流引擎。

## 7. 里程碑

### 7.1 V2.3：可门禁的 AgentScope/AgentTeams 验证

交付范围：

- V2.2 的 QualityReport、ComparisonReport、ReleaseGate；
- Reference A/B 的质量、对比和 Gate 产物已经进入 ReleaseEvidence；已知回归作为负向控制必须被阻断；
- real-backend Playwright、Skill contract 和故障矩阵；
- AgentTeams v1.2.2 双基线；
- AgentScope 2.0/AG-UI Driver；
- Target Capability Snapshot；
- 第一批 AgentScope 安全回归套件。

出口条件：对固定 AgentScope/AgentTeams 环境可重复执行 A/B，能解释每个回归、环境差异和权限事件，
并由 CLI/GitHub Check 阻断失败发布。

### 7.2 V2.4：生产证据转测试资产

交付范围：

- Project 最小边界；
- OTLP/HTTP ingest、ProductionSession/Trace/Span；
- Trace 搜索、详情和保留策略；
- Trace→TestCase/Sample draft 与来源关系；
- 人工 Annotation、EvaluatorVersion 和 AlignmentReport。

出口条件：一条经脱敏、人工确认的生产失败可生成 draft Case，经审核后进入 Suite，并可在固定
Capability Snapshot 上重放。

### 7.3 V2.5：失败模式与产品化

交付范围：

- Failure Pattern 与状态生命周期；
- 修复/复发关联、Monitor、Webhook/Slack；
- PostgreSQL lease/heartbeat 调度；
- Project 级 API key、策略和保留；
- 视需求增加 OIDC/RBAC、Helm 和多副本部署。

出口条件：已确认失败在 candidate 修复后可进入 resolved，上线后同类证据出现时自动标记 regressed，
且历史 Run、Gate 和人工决策均可追溯。

## 9. 跨专题 API 与 Schema 约定

新契约使用独立版本，不原地改变已有 v1 字段语义：

```text
agentrig.quality-report.v1
agentrig.comparison-report.v1
agentrig.release-policy.v1
agentrig.release-gate.v1
agentrig.driver-event.v2
agentrig.target-capability-snapshot.v1
agentrig.production-trace.v1
agentrig.annotation.v1
agentrig.alignment-report.v1
agentrig.failure-pattern.v1
```

Schema 统一要求：

- `schema_version`、稳定 ID、`created_at` 和来源字段；
- `extra="forbid"` 用于写入和产物契约；
- Secret 只记录引用是否存在，绝不记录值；
- 枚举新增遵守向后兼容，旧客户端遇到未知值不得崩溃；
- 时间使用 UTC ISO 8601，耗时使用明确的 `_ms` 后缀；
- 比例使用 `[0, 1]`，token 和费用区分计量值与估算值。

## 11. 风险与控制

| 风险 | 控制 |
|---|---|
| 追随外部 Runtime 导致 Driver 不稳定 | 通用事件 v2 + profile adapter；兼容矩阵固定版本 |
| 热加载导致历史运行不可复现 | Capability/Skill 内容哈希和 observed/verified 状态 |
| 生产 Trace 泄露敏感内容 | ingest allowlist、Redactor、Project policy、短保留和拒绝原因 |
| 自动 Judge 自我强化错误 | 人工金标、版本化、draft 激活、回放对齐 |
| 聚类误报被升级为产品事实 | candidate pattern 与 confirmed pattern 分开 |
| 过早建设重型基础设施 | 设定容量触发阈值，未达到前保持模块化单体 |
| P0/P2 并行造成范围失控 | V2.3 Gate/Driver/Snapshot 完成后才开放生产 ingest |

## 12. 明确否决的方案

1. 用 Latitude 或其他 Trace 后端替代 AgentRig 数据库作为审计真相。
2. 把所有 ProductionTrace 写成 Run/CaseRun。
3. 为适配 AgentScope 重写整个执行器或把 AgentScope 作为唯一 Runtime。
4. 原地删除 v1.1.2 部署文件和比赛证据。
5. 让 Target 的 `REQUIRE_USER_CONFIRM` 自动批准 AgentRig 的外部动作。
6. 在 V2.3 直接加入自动改代码、开 PR 或无人审批发布。
7. 用一个总分替代 pass/fail/inconclusive/evaluation_error 和原子证据。

- [x] v1.1.2 与 v1.2.2 profile/报告可并列生成，历史数据与资源未被改写；
- [x] AgentScope 权限、暂停恢复、模型调用和嵌套 Agent 事件可查询；
- [x] Capability 不一致时 A/B 产生 `incomparable_environment`，不会被误判为正常回归；
- [x] 生产证据默认关闭，启用需 Project/source/key、脱敏、配额和保留配置；
- [x] Trace→Case 只创建 draft，并保存 Span、mapping、审核和 tombstone lineage；
- [x] Judge 变更通过版本化 AlignmentReport 和独立人工审批；
