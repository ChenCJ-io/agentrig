# AgentRig V1 总体架构

> 状态：V1 实现基线
> 更新：2026-07-30

## 1. 产品边界

AgentRig 是 AI Agent 回归测试平台，不是业务 Agent 框架，也不在 V1 内部建设用例执行
助手。V1 优先服务外部 Codex、Claude Code 和人工控制方：

```text
Codex / Claude Code / Human
  ├─ 选择或构建 TestCase
  ├─ 选择 Target 和 ExecutionProfile
  ├─ 调用 run_cases
  ├─ 查询 Run / CaseRun 原子证据
  └─ 可选提交 External Verdict
                    │ MCP / HTTP
                    ▼
AgentRig V1 模块化单体
  ├─ Catalog：TestCase / Target / Profile / Sample
  ├─ Planner + Scheduler + CaseExecutor
  ├─ Provider Chain
  ├─ Rule / Evidence Judge / External Evaluations
  ├─ Event + Snapshot Repository
  └─ Web 人工管理界面
                    │ Driver / MCP Proxy
                    ▼
被测 Agent + 业务 MCP Tool Servers
```

V2 才会在平台内增加对话式用例执行助手，由主助手调用更多子 Agent。V1 的领域服务、
原子 MCP Tools 和异步 Run 将直接成为 V2 的工具层，不建设第二条执行链。

## 2. V1 的两个内置 Agent

### 2.1 Simulation Curator

它只负责生成工具结果，不负责修改用例、断言或评测要求。

输入：

- 当前工具名、参数和输出 Schema；
- `initial_state` 和本轮 `simulation_instruction`；
- 本 CaseRun 之前的脱敏事件；
- 本 CaseRun 的模拟状态。

输出：

- 结构化工具结果；
- 可选状态更新；
- Prompt 版本、模型信息、尝试次数和校验信息。

结果需要经过统一 Validator。首次不合法时，Curator 只得到校验反馈并修正一次。不同
CaseRun、版本、重复和 A/B 分支完全隔离；V1 默认每次执行重新生成，不缓存。

### 2.2 Evidence Judge

它只根据 rubric、Rule 输出和 CaseRun 的脱敏证据生成：

- `pass`、`fail` 或 `inconclusive`；
- 逐项 criteria；
- 引用真实 event ID 的 `evidence_refs`；
- 一段文字 summary。

Judge 不输出数值分。未知 Evidence 引用会触发一次修正；第二次仍无效则存档为
`evaluation_error`，不能伪装成 fail。

## 3. 一次运行的模型

`run_cases` 同时覆盖单用例和批量：

```text
Run
  └─ CaseRun = TestCase × Target × Version × Repeat
```

普通运行包含一个 candidate Target；A/B 包含 baseline 和 candidate 两个 Target。
两边使用 `comparison_pair_id` 配对，但 V1 不建设 Comparison Engine。

调用立即返回 Run ID。Planner 同步完成：

1. 解析明确 case IDs 或 selector；
2. 解析保存或临时 Target；
3. 合并项目默认、Profile 和本次 overrides；
4. 展开版本、重复和 A/B；
5. 检查 Driver 能力和评判配置；
6. 创建 executable 与 skipped CaseRun；
7. 冻结用例、Target 和 Profile 快照。

Scheduler 在进程内按批次并发执行。父 Run 的 `completed` 表示调度已经结束，不等于所有
CaseRun 都 pass。执行状态和评测结论始终分开。

## 4. 版本规则

- 明确传 version：只运行该版本；用例不支持时返回 skipped。
- 不传 version：按每个用例的 `supported_versions` 全部展开。
- Target 有对应版本覆盖时使用覆盖；否则使用 Target 默认配置并透传版本。
- Target 另外登记但用例不支持的版本会形成结构化 skipped 项，不静默丢弃。
- 用例支持 `*` 时，若 Target 登记了版本，则运行 Target 全部版本。
- 两边都无版本信息时运行一次 `version = null`。
- 版本是任意不透明字符串，不做 SemVer 范围推理。

批量中的不兼容项结构化跳过，不阻塞其他兼容项。

## 5. 三种工具方式

### controlled

被测 Agent 把工具调用作为 DriverEvent 交给 AgentRig；Provider 链生成结果后，Driver
将结果回灌。这是 AgentScope HTTP/SSE 和 OpenAI tool-calling 的典型方式。

### proxy

被测 Agent 自己连接 AgentRig MCP Proxy。每个 CaseRun 创建独享的短期 Scope：

- 随机 Scope Token 通过 Driver 注入；
- ACP Driver 在 `session/new` 中把 Scope URL 和 Header 作为 HTTP MCP Server 注入；
- Proxy 中的工具调用使用该 CaseRun 的 Provider 链；
- Fixture 消费位置、Sample 序列和 Curator 状态不跨运行共享；
- 所有调用、Provider 尝试、校验和结果写入该 CaseRun 事件；
- 运行停止后立即撤销 Scope。

Proxy 的工具目录按以下来源合并：

1. 部署配置的真实后端 MCP Server；
2. Target `options.tool_catalog` 中声明的 MCP-native 工具 Schema；
3. 用例 Fixture 自动推导的最小工具 Schema。

因此像 Goose 这样自身没有业务 MCP 工具的 Agent，也能直接使用用例 Fixture。只使用
Sample 或 Simulation Curator、且没有真实后端时，Target 应通过 `tool_catalog` 声明工具，
工具定义和工具结果来源保持正交。

如果 Profile 包含 Real Tool，则 Proxy 可将调用放行到带命名空间的后端 MCP Server。

### observe_only

被测 Agent 自己执行工具；AgentRig 只能保存 Driver 能观察到的调用，不能注入结果。用例
含 Fixture 或 Curator 要求而 Driver 只能 observe 时，Planner 直接跳过。

## 6. Provider Chain

Profile 可按需排列：

```text
Fixture → Sample → Simulation Curator → Real Tool → fail
```

每次尝试都保存 `provider_attempt`。未配置、不可用、未命中或结果校验失败时继续下一个。

- Fixture：用例轮次私有，按书写顺序，默认一次消费。
- Sample：共享库中人工 approved 的单次或序列结果；匹配工具、版本和规范化参数。
- Curator：调用可选模型动态生成，且与断言/rubric 隔离。
- Real Tool：默认关闭；部署 allowlist、Profile 启用和用户授权必须同时成立。

Real Tool 结果不会自动创建 Sample。控制方只能用已存档的 `source_tool_call_id` 显式创建
draft，之后由人工在 Web 审核。

## 7. 评判

同一个 CaseRun 最多各保存一份：

- Rule Evaluation；
- Evidence Judge Evaluation；
- External Controller Evaluation。

Rule 在存在结构化断言时总会存档，即使它不是主评判器。External Verdict 可重复提交并
覆盖自己的当前记录，但不修改 Rule、Judge、执行状态、事件或完成时间。

典型组合：

- 不想配置模型 Key：主评判器使用 `external_controller`，Codex/CC 读取证据后回写。
- 希望平台语义判断：主评判器使用 `evidence_judge`。
- 确定性场景：主评判器使用 `rule`。

## 8. 数据与安全

V1 使用 11 张表：

```text
test_cases        case_turns       case_tags
targets           target_versions
execution_profiles
samples
runs              case_runs        run_events
evaluations
```

SQLite 和 PostgreSQL 使用同一套 async SQLAlchemy Repository 与 Alembic migration。
CaseRun 冻结执行所需快照；删除当前 Target/Profile 不影响历史证据。

所有事件落库前统一脱敏，之后 Curator、Judge、MCP、HTTP 和 Web 只能看到脱敏副本。
Target、模型和服务访问 Token 只接受 `env:VARIABLE_NAME` 引用；任意 JSON 配置、
用例初始状态和 Sample 中
出现明显凭据键会被拒绝。

MCP 不暴露用例/Sample 审核工具。人工审核仅在 HTTP/Web 中完成。

Target 写入和 `check_target` 共用当前部署的 Driver 预检。ACP 会在启动前校验命令数组、
相对路径对应的 `cwd`、规范化后的可执行文件 allowlist、Secret 与 `credential_env` 配对、
隔离目录配置和 `tool_catalog` Schema；静态校验通过后实际完成一次不发送 prompt 的
ACP initialize/session 探针。allowlist 的实际服务器路径不通过 MCP 暴露。

编码 Agent 可读取 Driver/Target/Profile/Sample/Run 的 JSON Schema。CaseRun 完整详情仍
保留，长事件流可通过 `list_case_run_events` 按类型分页读取；返回的 `event.id` 可直接作为
External verdict 的 `evidence_refs`。

## 9. 部署边界

V1 是单进程模块化单体：

- Scheduler 和 Proxy Scope 在进程内；
- 重启时 queued/running CaseRun 标记 interrupted；
- 不支持多副本共享 Scheduler/Scope；
- Web 轮询 HTTP，不建设 Run WebSocket；
- 默认只监听 `127.0.0.1`，公网部署必须通过 `server.api_token_ref` 配置访问 Token，
  并使用反向代理。

需要水平扩展时，再将 Scheduler、队列和 Proxy Scope 迁到外部协调组件；领域服务、事件
契约和数据库表不需要重写。
