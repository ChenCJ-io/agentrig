## 1. 产品边界

AgentRig 是 AI Agent 的**回归评测运行时与发布门禁基础设施**，不是 Agent 框架，也不是业务
Agent。它只做一件事：让每一次 Agent 变更都经过可复现、可审计、可回归的验证。

整个代码库围绕一条不变量组织：

> **所有结论必须能从不可变证据派生。任何组件都不能靠一段看似成功的文本改写运行事实，
> 也不能绕过确认、权限或证据门禁。**

它在实现中落为三条硬分离：

| 分离 | 实现位置 |
|---|---|
| 执行状态 ≠ 评测结论 | `case_runs.status` 与 `case_runs.evaluation_state` 是两列；`completed ≠ pass` |
| 生成证据的角色 ≠ 裁决的角色 | Curator 只产工具结果；Judge 只读冻结证据；Core 独占状态与权限 |
| 控制面 ≠ 执行面 | 助手与外部控制方只能「预览 → 确认 → 提交」，不能直接写入评判事实 |

| 角色 | 负责 | 明确不负责 |
|---|---|---|
| 评测助手 / 外部控制方 | 理解目标、查询资产、形成计划、解释结果 | 绕过用户确认、直接写入评判事实 |
| Simulation Curator | 可靠样本缺失时生成并校验受控工具结果 | 调用真实业务工具、决定 pass/fail |
| Evidence Judge | 依据 rubric 与冻结证据独立裁决并引用事件 | 修改 RunEvent、补造不存在的证据 |
| AgentRig Core | 执行、权限、状态机、证据、Rule 与审计事实 | 依赖模型或聊天文本才能保持正确性 |

## 2. 控制面与对外入口

一个 `agentrig serve` 进程暴露六个面，全部在 `src/agentrig/app.py:45` 装配：

| 入口 | 挂载 | 用途 | 鉴权 |
|---|---|---|---|
| `/api/*` | `v1_api.py` | 资产、运行、报告、门禁、项目域治理 | 部署 Bearer token 或项目 `agrp_` key |
| `/api/v2/*` | `v2_api.py` | 助手会话与 SSE、EvaluationPlan 状态机、Target 直连会话 | 同上 |
| `/mcp/` | `mcp_server.py` + `mcp/tools/` | 41 个原子工具 + `ping`，供 Codex/Claude Code 等编码 Agent 控制评测 | 同上 |
| `/proxy` | `proxy/aggregator.py` | CaseRun 级 MCP Proxy，被测 Agent 自己连接 | Scope token（+ 部署 token） |
| `/v1/traces` | `production/api.py` | 标准 OTLP/HTTP 生产 Trace 接收（protobuf 与 JSON） | 接入源独立 token，**不接受部署级 token** |
| `/gateway/{source_id}/v1/*` | `production/gateway.py` | OpenAI 兼容网关车道，转发并旁路记录 | 接入源 token |
| `/` | `web/dist/client` | React Router SPA 管理界面 | 公开静态资源 |

另有两个非 HTTP 控制面：`agentrig` CLI（`test` / `report` / `gate` / `safety` / `worker` /
`db` / `demo` / `serve`）与项目级 API Key 的 scope 映射（`app.py:193`，按路由收敛到
`read` / `run` / `ingest` / `review` / `admin`）。

默认只监听 `127.0.0.1`。公网暴露必须配置 `server.api_token_ref` 并使用反向代理，详见
[快速开始与安全部署](./08-快速开始与安全部署.md)。

## 3. 分层模块地图

依赖方向始终从入口指向 Service，再指向 Repository 与 Driver/Provider 协议。HTTP 与 MCP 入口
不直接访问 ORM，也不互相编排。

```text
装配层    app.py  bootstrap.py  config.py  cli.py  mcp_server.py
            │  ServiceContainer.build() 是唯一装配点（手工 DI，无框架魔法）
            ▼
接口层    v1_api  v2_api  mcp/tools  production/api  production/gateway  proxy
            ▼
领域层    ┌ 资产   cases  targets  profiles  tool_results(samples)  projects
          ├ 执行   runs(planner/executor/scheduler/manifest)  jobs  capabilities
          ├ 判定   evaluations  agents  reporting  gates  safety
          └ 生产   production  reviews  failures  observability
            ▼
适配层    targets/drivers(8)   tool_results/providers(4)   agents(模型端口)   proxy
            ▼
```

`bootstrap.py` 是理解依赖关系最快的入口：任何对象怎么构造、依赖谁，都在这 350 行里。

## 4. 执行模型：Run → Cell → Attempt

`run_cases` 一个入口同时覆盖单用例、批量、多版本、重复与双 Target A/B：

```text
Run                                               一次提交，持有 RunManifest 与稳定哈希
 └─ Cell    = TestCase × Target(role) × Version   逻辑坐标，由 cell_key 标识
     └─ Attempt = 一次 repeat                     一行 case_runs，是执行单元也是证据单元
```

- `case_runs` 既承载执行也承载证据；`repeat_index` 与 `attempt_index` 表达重复与恢复尝试。
- Cell 是查询时聚合出来的视图（`runs/service.py:138`），不是独立表。
- 普通运行只有 candidate；A/B 有 baseline 与 candidate 两侧，通过 `comparison_pair_id` 配对。
- 父 Run 的 `completed` 只表示调度结束，不表示全部 Attempt 通过。
- RunManifest（`runs/manifest.py`）把选择、三份快照身份与全部 Cell/Attempt 序列化为 canonical
  JSON 并哈希，是报告与门禁可复算的基础。

```text

        ▼
RunPlanner.plan()                                         runs/planner.py:102

  4 _preflight(): 校验 Driver 能力与评判配置，不兼容项结构化 skipped
```

Driver 契约见 `targets/drivers/base.py`：所有协议归一到 `DriverEvent`
（`agentrig.driver-event.v2`，31 种类型），能力由 `DriverCapabilities` 的 19 个布尔位声明，
Planner 的 preflight 就以此为依据。Driver 可选实现 Configurable / Probeable / Describable /
Resumable / PermissionResponse / ExternalExecution 六个 Protocol。

## 6. 三种工具方式与 Provider 链

ExecutionProfile 的 `tool_mode` 决定工具调用由谁执行：

### controlled

被测 Agent 把工具调用作为 DriverEvent 交给 AgentRig；Provider 链产出结果后由 Driver 回灌。
AgentScope HTTP/SSE 与 OpenAI tool-calling 的典型方式。`python_agent` 在被测进程的框架层完成
同样的交接，Agno 与 LangGraph Agent 不需要改造成外置工具循环，见
[Python Agent 接入指南](./05-Python-Agent接入指南.md)。

### proxy

被测 Agent 自己连接 AgentRig MCP Proxy。每个 CaseRun 独享一个短期 Scope：

- 随机 Scope Token 通过 Driver 注入；ACP Driver 在 `session/new` 中把 Scope URL 与 Header
  作为 HTTP MCP Server 注入；
- Proxy 内的调用使用该 CaseRun 的 Provider 链；Fixture 消费位置、Sample 序列与 Curator 状态
  不跨运行共享；
- 所有调用、Provider 尝试、校验与结果写入该 CaseRun 事件；运行停止即撤销 Scope。

Proxy 的工具目录按三个来源合并：部署配置的真实后端 MCP Server、Target `options.tool_catalog`
声明的 MCP-native 工具 Schema、用例 Fixture 自动推导的最小 Schema。因此像 Goose 这样自身没有
业务 MCP 工具的 Agent 也能直接使用用例 Fixture；工具定义与工具结果来源保持正交。

### observe_only

被测 Agent 自己执行工具；AgentRig 只保存 Driver 能观察到的调用，不能注入结果。用例含 Fixture
或 Curator 要求而 Driver 只能观察时，Planner 直接跳过。AG-UI、subprocess 与 python_agent 观察到的
工具结果只保存 sha256 摘要，不导出正文。

### Provider 链

```text
fixture → sample → simulation_curator → real_tool → fail
```

每次尝试都保存一条 `provider_attempt` 事件。未配置、不可用、未命中或结果校验失败时继续下一个，
全部失败抛 `ProviderExhausted`（`tool_results/chain.py:88`）。

- **Fixture**：用例轮次私有，按书写顺序，默认一次消费。
- **Sample**：共享库中人工 approved 的单次或序列结果；匹配工具、版本与规范化参数。
- **Curator**：调用可选模型动态生成，与断言/rubric 隔离。结果过统一 Validator，首次不合法时
  只得到校验反馈并修正一次。不同 CaseRun、版本、重复与 A/B 分支完全隔离，默认不缓存。
- **Real Tool**：默认关闭。部署 allowlist、Profile 启用与用户授权必须同时成立。

Real Tool 结果不会自动创建 Sample。控制方只能用已存档的 `source_tool_call_id` 显式创建 draft，
再由人工在 Web 审核。

## 7. 版本规则

- 明确传 version：只运行该版本；用例不支持时返回 skipped。
- 不传 version：按每个用例的 `supported_versions` 全部展开。
- Target 有对应版本覆盖时使用覆盖；否则使用 Target 默认配置并透传版本。
- Target 登记但用例不支持的版本形成结构化 skipped 项，不静默丢弃。
- 用例支持 `*` 时，若 Target 登记了版本，则运行 Target 全部版本。
- 两边都无版本信息时运行一次 `version = null`。
- 版本是任意不透明字符串，不做 SemVer 范围推理。

批量中的不兼容项结构化跳过，不阻塞其他兼容项。

## 8. 评判与报告

同一个 CaseRun 最多各保存一份 Rule Evaluation、Evidence Judge Evaluation 与 External
Controller Evaluation。存在结构化断言时 Rule 总会存档，即使它不是主评判器。External Verdict
可重复提交并覆盖自己的当前记录，但不修改 Rule、Judge、执行状态、事件或完成时间。

Evidence Judge 只输出 `pass` / `fail` / `inconclusive`、逐项 criteria、引用真实 event ID 的
`evidence_refs` 和一段 summary，不输出数值分。未知 Evidence 引用触发一次修正；第二次仍无效则
存档为 `evaluation_error`，不能伪装成 fail。

典型组合：不配置模型 Key 时主评判器用 `external_controller`，由 Codex/CC 读证据后回写；需要
平台语义判断时用 `evidence_judge`；确定性场景用 `rule`。

终态 Run 之上派生四类可复算产物，全部带稳定来源哈希与结果哈希：

| 产物 | 入口 |
|---|---|
| `RunReport` | `GET /api/runs/{id}/report` |
| `QualityReport`（`agentrig.quality-report.v2`） | `GET /api/runs/{id}/quality-report`、`agentrig report` |
| A/B `ComparisonReport` | `GET /api/runs/{id}/comparison-report` |
| `ReleaseGateResult` / `SafetyReport` | `POST /api/runs/{id}/release-gate:evaluate`、`agentrig gate` / `agentrig safety` |

## 9. 生产证据与治理闭环

生产 Trace 与测试 Run 是**两个事实域**。采样 Trace 永远不能变成执行真相；两者只通过显式
lineage 关联。

```text
线上应用
  ├ 改 base_url ──► /gateway/{source}/v1/…  转发 + 旁路记录（SSE 透传边转边攒）
  └ OTel 埋点  ──► /v1/traces               protobuf 与 JSON，同一套归一化
                          ▼
            ProductionSession / Trace / Span
            接入源级 token、限流、retention、脱敏策略三档
                          ▼
            Trace → Case 草稿（预览 / 创建 / lineage 人工审核）
            真实工具调用自动生成 Sample 草稿 → 人工审核 → 重放不触发副作用
                          ▼
            ReviewItem → Annotation → GoldLabel → EvaluatorVersion → AlignmentRun
            FailureSignal → Pattern → Monitor → 签名幂等 Webhook
```

隐私默认值保守：不显式开启就不存正文。三档策略为「全关（只存元数据与结构化字段）」、
`save_*_preview`（脱敏截断预览）、`save_full_content`（脱敏后完整消息与工具参数/结果，
转用例所需）。全文同样先过 Redactor，有单条体积上限，并随接入源 `retention_days` 一起清理。

接入配方与向导见[生产 Trace 接入指南](./04-Trace接入指南.md)；方案背景与分期见
[AR-RFC-0005](./11-一站式Trace接入与生产回归闭环-RFC.md)。

## 10. 数据与安全

当前共 39 张表，按域分组：

```text
项目隔离  projects  environments  project_api_keys
资产      test_cases  case_turns  case_tags  targets  target_versions
          execution_profiles  samples
运行证据  runs  case_runs  run_events  evaluations
V2 助手   assistant_sessions  assistant_events  assistant_turns
          evaluation_plans  target_chat_sessions
生产证据  ingest_sources  production_sessions  production_traces
          production_spans  trace_case_lineages
评审治理  review_items  annotations  gold_labels  evaluator_versions  alignment_runs
故障治理  failure_signals  failure_patterns  failure_pattern_memberships
          failure_monitors  failure_pattern_events  failure_notifications
          governance_audit_events
耐久执行  execution_jobs  execution_attempts  worker_registrations
```

SQLite 与 PostgreSQL 共用同一套 async SQLAlchemy Repository 与 Alembic migration（当前 head
`20260908_0010`）。持久化数据库启动前强制校验 revision，不会由 ORM 元数据静默补表；只有隔离的
内存测试库由测试装配代码建表。CaseRun 冻结执行所需快照，删除当前 Target/Profile 不影响历史证据。

安全不变量：

| 不变量 | 落点 |
|---|---|
| 脱敏单点 | 只有 `EventRecorder` 能落库且必过 `Redactor`；Curator、Judge、MCP、HTTP、Web 只看脱敏副本 |
| 凭据只引用 | Target、模型与服务 Token 只接受 `env:VARIABLE_NAME`；配置、用例初始状态与 Sample 中出现明显凭据键会被拒绝 |
| 快照冻结 | 报告与门禁只读终态 Run 的冻结事实，不回查当前资产 |
| 副作用围栏 | Real Tool 执行**前**先持久化 `external_side_effect`，该 Job 从此不重试（`jobs/service.py:516`） |
| 幂等与恢复 | 重启把 queued/running 标 `interrupted`；恢复跑生成**新 Run**，不覆盖旧证据 |
| 审核不走 MCP | 用例与 Sample 的人工审核只在 HTTP/Web 完成，MCP 工具面不注册审核工具 |
| 最小权限面 | 项目 API Key 按路由收敛 scope；allowlist 的真实服务器路径不通过 MCP 暴露 |
| 出站受控 | Target 与 Webhook 的 HTTP(S) 出站校验 URL、私网地址、DNS 解析与主机 allowlist |

Target 写入与 `check_target` 共用当前部署的 Driver 预检。ACP 会在启动前校验命令数组、相对路径
对应的 `cwd`、规范化后的可执行文件 allowlist、Secret 与 `credential_env` 配对、隔离目录配置和
`tool_catalog` Schema；静态校验通过后实际完成一次不发送 prompt 的 ACP initialize/session 探针。

编码 Agent 可读取 Driver/Target/Profile/Sample/Run 的 JSON Schema。CaseRun 完整详情保留，长
事件流可通过 `list_case_run_events` 按类型分页读取；返回的 `event.id` 可直接作为 External
verdict 的 `evidence_refs`。RunEvent 共 23 种类型。

## 11. 部署边界

AgentRig 是单进程模块化单体，有两种执行形态：

| 形态 | 开关 | 适用 | 限制 |
|---|---|---|---|
| 进程内调度 | 默认 | 单机、本地开发、CI | Scheduler 与 Proxy Scope 在内存，不支持多副本；重启把 queued/running 标 `interrupted` |
| 耐久执行 | `execution.durable_scheduler_enabled = true` | 多 Worker、重启续派、生产试点 | 需要 PostgreSQL 才有实用并发；Proxy Scope 仍在各 Worker 进程内 |

其余边界：Web 轮询 HTTP，不建 Run WebSocket（助手用轮询式 SSE 并支持 `after_seq` 续传）；
网关在请求路径上，定位为开发与预发首选，生产推荐带外 OTLP 车道；高频接入推荐 PostgreSQL。

需要进一步水平扩展时，把 Proxy Scope 迁到外部协调组件即可；领域服务、事件契约和数据库表
不需要重写。
