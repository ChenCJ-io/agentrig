## 一、当前执行模型实勘（Lassist 现状）

**当前 = tool-calling 往返的「SSE 中间人」**。

平台 POST 到被测 agent 的 `/chat/stream` → agent 在 SSE 流里 yield `tool_calls` 事件 → 平台拦截 → `mock_hub.generate_result()` 实时生成结果 → 组装 `tool_result` POST 回同一 endpoint → agent 继续（可递归）。这是 Lassist 私有协议的一种实现，**本质是 tool-calling 调用-返回往返**。

**关键利好**：机判（`rule_judge` / `arg_assert`）吃归一化的 `round_data`，**不吃原始 SSE**（字段口径弱：`tool_calls[].name/arguments`、`assistant_text`、`validation_results`）。换协议时只要 adapter 把事件归一成 `round_data`，**机判几乎不动**。

**协议耦合点（4 层，深度不均）**：

| 层 | 耦合点 | 改造 |
|---|---|---|
| 传输/协议 | `agent_client.py`：`/chat/stream`、`type:chat/tool_result`、`device_info`、SSE 事件 type、`async_pending`/`user_input` 回执 | **重**——抽象成 `AgentTransport` 接口 |
| L3 兜底模拟器 | `tool_simulator.py` 全部 `_handle_*` + `TOOL_RESULT_EXAMPLES` + Qwen prompt | **重，可整层弃用**（proxy 模式下用不上） |
| 机判/断言 | `rule_judge`（`_is_internal_tool` 白名单）、`arg_assert` | **轻**——字段已归一 |
| case DSL | `case_adapter.py`（`attachments`/`metadata.masks`/`project_state`）、`mock_script` `@resource`、`tool_registry` | **中**——Lassist 业务概念需泛化 |

## 二、核心分野：工具调用「外置」vs「内置」

> ⚠️ 这一节修正上一版「MCP 零 hack 最优雅」的错误表述。真相正好相反。

|  | 外置工具 | 内置工具 |
|---|---|---|
| tool_call 在哪 | 协议里外露（和对话同一个流） | agent 内部闭环（对话只有 POST /chat） |
| AgentRig 角色 | **天然中间人** | 只是发消息的客户端（黑盒） |
| 例子 | **Lassist**、部分 streaming chat | Claude Code、Cursor、**大多数 MCP agent**、OpenAI Assistants |
| AgentRig 接入难度 | 最舒服（特例优势） | 要靠 proxy / 配置接入 |

- **Lassist 是外置特例 = AgentRig 最舒服的模式**（不是包袱）。它恰好让 AgentRig 天然中间人，是「协议中间人」模式的标杆参考实现。
- **标准 MCP agent 是内置常态 = 最难的模式**。agent 自己持 MCP client、自己连工具 server、自己闭环，对外只有 `POST /chat`。AgentRig 只看到「请求进去、最终回复出来」，**中间工具调用是黑盒**。

> 这才是上一轮那个问题的本质：不是「对话协议怎么适配」（表象），而是 **「工具调用的黑盒怎么打开」**。

## 三、内置工具的黑盒怎么打开？4 种手段

按侵入度从轻到重：

**① 工具替换（配置级）** —— agent 测试时把工具源配成 AgentRig（改 mcp config / tool 定义）。agent 调工具 → 实际调到 AgentRig → 按剧本返回 mock。中间态天然在 AgentRig 手里。**问题**：要 AgentRig 实现 mock 工具，多 MCP / 版本化场景下别扭。

**② 工具代理 / 聚合（配置级）★ MCP 主推** —— AgentRig 做 MCP proxy/aggregator，agent 配 AgentRig 一个，AgentRig 后挂 N 个真实 server。选择性 mock + 全量 trace + 真实透传。详见第四节。

**③ Trace 上报（instrumentation 级）** —— agent 真跑（用真实工具），通过 OTLP / 框架 callback 把 tool_call/tool_result **主动上报** AgentRig。**只观测不干预（不能 mock）**。零侵入、任何 agent 都能用，但和 Langfuse 同质化、回归抖动。

**④ 框架 SDK hook（代码级）** —— 给 LangGraph/CrewAI/自研框架写 adapter，hook 在工具调用层，既上报又可注入 mock。逐框架铺。

| 手段 | 侵入 | 能 mock | 能断言 | 稳定回归 | 适用 |
|------|------|--------|--------|---------|------|
| ① 工具替换 | 配置级 | ✅ | ✅ | ✅ | 单 MCP / 简单 agent |
| **② MCP proxy** ★ | 配置级 | ✅ | ✅ | ✅ | **MCP agent 主推** |
| ③ Trace 上报 | instrument | ❌ | ⚠️事后 | ❌ | 兜底/入门 |
| ④ SDK hook | 代码级 | ✅ | ✅ | ✅ | 主流框架逐个铺 |

## 四、MCP 模式正解：Proxy / Aggregator

### 双重身份

AgentRig 做代理时：**对 agent 是 MCP server，对后端真实 server 是 MCP client**。

```
agent（MCP client）
   │  tools/list, tools/call（JSON-RPC）
   ▼
AgentRig（MCP Proxy：对上是 server，对下是 client）
   │  按工具名前缀路由 + 选择性 mock + 全量 trace
   ├──────────┬──────────┬──────────┐
   ▼          ▼          ▼
fs server  git server  biz server（真实 MCP）
```

### 转发 + mock + trace 一条链路（简化伪码）

```python
class AgentRigProxy:
    """对 agent 是 MCP server，对后端是 MCP client。"""

    def __init__(self, backends, mock_policy, trace_sink):
        # backends: {"fs": MCPClient(...), "git": MCPClient(...), "biz": MCPClient(...)}
        self.backends = backends
        self.mock = mock_policy       # 当前测试场景的 mock 策略（L0/L1/L2）
        self.trace = trace_sink       # 工具调用全部落 trace

    # ① tools/list → 聚合所有后端工具，加命名空间前缀（防撞名）
    async def tools_list(self):
        tools = []
        for name, client in self.backends.items():
            for t in await client.list_tools():        # 动态发现后端工具
                tools.append({
                    "name": f"{name}__{t.name}",        # fs__read_file
                    "inputSchema": t.inputSchema,        # 透传签名，AgentRig 不持有
                })
        return tools

    # ② tools/call → 路由 + mock + trace
    async def tools_call(self, namespaced, arguments):
        self.trace.tool_call(namespaced, arguments)            # trace 记录输入
        if self.mock.should_mock(namespaced, arguments):      # 本次要不要 mock？
            result = self.mock.generate(namespaced, arguments) # 剧本/样本库返回
            self.trace.tool_result(namespaced, result, "mock")
            return result
        backend, real = namespaced.split("__", 1)              # 拆前缀
        result = await self.backends[backend].call_tool(real, arguments)  # 转发真实 server
        self.trace.tool_result(namespaced, result, "real")
        return result
```

> 这套 aggregator 模式不是 AgentRig 发明（参考 [MetaMCP](https://www.linkedin.com/posts/shubhamsaboo_you-can-now-turn-chaos-of-mcp-servers-into-activity-7354336359580336128-TpzE) / [Discussion #94](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/94)）。AgentRig 的独特性在 **proxy 链路里插了 mock + trace 层**——这是 Langfuse/MetaMCP 都不做的。
>
> 顺带回答了「怎么获取中间态」：trace 就在 proxy 链路里产生（`self.trace.tool_call/tool_result`），**不用去数据库读别人的链路**。工具调用从 AgentRig 过，它天然有最全的工具 trace。

### 解决两个核心顾虑

**多 MCP 怎么办** —— agent 的 mcp config 从「直接配 N 个真实 server」改成「配 1 个 AgentRig，它代理那 N 个」。一次性配置。被测工具走 mock，其他透传真实 server。

**版本化怎么办** —— MCP 工具级版本化是**业界公认 gap**（[Issue #1039](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1039)，标准无 `version` 字段）。业界做法：工具名带版本（`search_v2`，最常见）/ 直接演进 / 多工具并存 / 自定义 annotations。**AgentRig 作为 proxy 不持有工具签名**（透传后端 `inputSchema`），所以**不绑任何版本、不背版本债**。mock 按「工具名 + 参数匹配」，后端演进时调整剧本即可，是测试用例维护成本，不是架构债。

> proxy 模式相对「工具替换/实现」模式的最大优势就在这：如果要 AgentRig 自己实现工具 mock，它就得跟每个版本；proxy 只转发，把版本化的锅还给后端 server。

## 五、AgentRig 的差异化：工具层测试 vs 对话层观测

这才是 AgentRig 占的位置——和 Langfuse/promptfoo 的**本质分界**：

| | Langfuse / promptfoo | **AgentRig** |
|---|---|---|
| 测试层 | 对话层 / 输出层 | **工具层** |
| 怎么接入 agent | 观测 SDK / 事后判别输出 | **MCP proxy，工具调用从它过** |
| 能 mock 工具 | ❌ 只观测不干预 | ✅ 选择性 mock 任意工具 |
| 能断言工具调用 | ⚠️ 只能事后看 | ✅ 该不该调 / 参数 / 顺序 |
| 回归稳定性 | 工具真实返回，会抖动 | ✅ 控制工具返回 = 控制变量 = 稳定回归 |

**Langfuse 做不到工具层测试**——它不在 agent 和工具之间，所以不能 mock。**AgentRig 占的是「工具中间层」这个位置**，这在 MCP 之前不存在（每家工具协议私有），是 MCP 把工具调用标准化后才打开的新层。

### 「发起 + 读 trace 库判别」是降级模式，不是主模式

这条路（agent 真跑 + 事后读 trace 判定）可行但：
- ❌ 不能 mock → 不能测「工具返回错误/边界数据时 agent 怎么应对」
- ❌ 回归抖动 → 工具返回真实不确定，今天过明天挂
- ❌ 和 Langfuse 同质化 → 没有差异化理由

定位为**零侵入入门/兜底**（agent 不愿配 proxy 时用），**不当主推**。主推必须是「能干预工具」的 MCP proxy 模式。

## 六、定位 sharpen：MCP 时代的工具层测试台

> **MCP 之前**，工具调用各 agent 私有，工具层测试不可能标准化 → 只能测对话输出（Langfuse/promptfoo 领地）。
> **MCP 之后**，工具调用标准化，**「工具层测试」第一次成为独立、通用、标准的层**。
> AgentRig 占这个层——不是「又一个 eval 工具」，是「MCP 让工具层可测」这件事的第一个产品。

这 framing 让「为什么是现在 / 为什么是 MCP / 为什么不是 Langfuse」三个问题一次答完。前提是 MCP 普及（趋势在，但不是稳赢）。

> 工具层测试是**产品愿景飞轮**（见 `01`）的技术支撑：proxy 录的 trace = CC 写用例的真实数据来源；proxy 的 mock = 飞轮回放稳定性的保障。技术层和产品层同源——这不是两件事，是一次投入。

**接入边界**（已同步 `01-定位与命名.md`）：
- **MCP agent**：首选。AgentRig 作 proxy，配置级接入，完整 mock 能力。
- **其他 tool-calling agent**（OpenAI/Anthropic/LangGraph）：作 tool 中间人，写 transport adapter。
- **非 tool-calling agent**：退化纯观测模式。

## 七、两个「版本」概念厘清（别混）

| | 是什么 | 谁管 |
|---|---|---|
| **MCP server 工具的版本** | 外部 MCP server 暴露的工具怎么演进 | 后端 server 自己（MCP 无 standard） |
| **AgentRig 的 `tool_manager` 管的版本** | **被测 agent 自己的工具定义/prompt** 的版本演进 | AgentRig（现有 `tool_manager.py` 主版本+分支同构） |

这俩正交：proxy 转发的是前者，`tool_manager` 管的是后者。**后者是 AgentRig 现成的差异化能力（Langfuse 没有），开源必须保留**。
