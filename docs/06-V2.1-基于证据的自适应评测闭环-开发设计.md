# AgentRig V2.1：基于证据的自适应评测闭环开发设计

> 状态：已实现并通过本地真实链路验收
>
> 版本：1.1
>
> 日期：2026-08-04
>
> 前置架构：`03-V2-智能评测助手与AgentTeams-开发设计.md`
>
> 前置产品设计：`05-V2-完整产品与界面开发设计.md`
>
> 适用范围：AgentRig Managed Web、AgentTeams Manager/Worker、比赛演示与后续产品化

本文定义 AgentRig V2.1 的核心增强：把当前已经可运行的“对话—计划—执行—评判”链路，升级为
可审计、可解释、可恢复的自适应评测闭环。本文是 V2.1 后端、Agent、前端和测试的直接开发依据。

本文不替代 V1 执行语义，也不推翻 V2 三 Agent 架构。若与 03、05 文档冲突：V1 的 Run、CaseRun、
Evidence、Evaluation 与权限边界仍以 03 文档为准；自适应决策、决策展示和恢复行为以本文为准。

---

## 0. 最终结论

AgentRig V2.1 最有说服力的核心能力不是“一键执行一条固定工作流”，而是：

> Manager 根据用户目标、资产状态、运行证据和安全策略，动态选择下一步；AgentRig Core 对选择做
> 确定性校验与执行；每个判断都能追溯到证据、计划、Run 和实际 Worker 调用。

完整闭环为：

```text
Observe 观察事实
  → Ground 绑定证据
  → Decide 形成结构化决策
  → Gate 执行策略校验
  → Act 调用受限领域动作
  → Verify 验证动作结果
  → Record 固化决策与证据关系
  → Explain 向用户解释并继续下一轮
```

它必须同时满足五个条件：

1. **真的会分支**：不是每次都机械调用 Manager、Curator、Judge。
2. **分支有依据**：所依据的 Case、Sample、Target、Profile、Run/Event/Evaluation 都有稳定引用。
3. **动作受约束**：模型提出动作，Core 决定允许、需确认或拒绝。
4. **结果可复现**：Plan 和 Run 继续冻结快照，决策保存上下文哈希和输出引用。
5. **失败可恢复**：系统区分传输故障、Worker 输出错误、被测 Agent 失败和证据不足，不擅自重跑或
   篡改结论。

V2.1 只新增一个核心业务事实对象：`DecisionRecord`。现有对象全部复用：

```text
AssistantSession
  └─ AssistantTurn
       └─ DecisionRecord
            ├─ EvaluationPlan revision
            │    └─ Run
            │         └─ CaseRun
            │              ├─ Event / Evidence
            │              ├─ AgentInvocation (Curator / Judge)
            │              └─ Evaluation
            └─ 后续 DecisionRecord（诊断或恢复）
```

V2.1 不建设通用工作流引擎，不增加第二套 Run，不让 Agent 绕过确认，不保存模型隐藏思维过程。

## 1. 背景与当前缺口

### 1.1 已有能力

当前 V2 已经具备：

- AgentTeams Manager 作为唯一面向用户的智能评测助手；
- Simulation Curator 与 Evidence Judge 两个独立 Worker；
- AssistantSession、AssistantTurn 与追加式 AssistantEvent；
- 可预览、可确认、可提交、可修订的 EvaluationPlan；
- V1 Planner、Scheduler、Provider Chain、CaseExecutor 和 Evaluation 执行内核；
- AgentInvocation 的输入快照、哈希、重试次数、Matrix 事件和结果引用；
- 三栏式智能评测助手、Run 详情、用例、样本、工具与 Target 管理界面。

### 1.2 仍缺少的产品事实

当前系统能够执行，但“为什么这样执行”主要散落在：

- Manager 的自然语言回复；
- `EvaluationPlan.reasoning_summary`；
- AgentTeams/Matrix 协作消息；
- Provider attempt 和 AgentInvocation 事件；
- Run 完成后的诊断文字。

这些内容尚未形成一个可查询、可验证的领域对象，因此目前难以直接回答：

1. Manager 当时看到了哪些事实？
2. 它考虑过哪些合法选项？
3. 为什么选这个范围、Provider 和 Evaluator？
4. 这个决定是否要求用户确认？
5. 决定最终产生了哪个 Plan、Run 或 Invocation？
6. 执行结果是否证明这个决定有效？
7. 失败后为什么重试、修订计划或停止？

### 1.3 V2.1 要解决的问题

V2.1 把上述问题统一为“决策链”，使评测助手从会聊天、会调用工具，提升为：

- 能根据事实选择不同路径；
- 能解释选择但不泄露隐藏思维链；
- 能把语义判断交给 Agent，把安全和状态机留给 Core；
- 能在不确定时停止并向用户索取最小必要信息；
- 能从终态证据提出下一步，但不越权执行新的业务 Run。

## 2. 目标、非目标与成功标准

### 2.1 P0 目标

1. 将 Manager 的关键业务决策保存为结构化 `DecisionRecord`。
2. 每个可变更状态的 Managed 动作必须关联一个有效决策。
3. 同一目标在不同资产/证据状态下产生可验证的不同执行路径。
4. Worker 只在需要时被实际调用，并能从决策追踪到 Invocation 和结果。
5. 运行结束后形成证据化诊断；证据不足时返回 `inconclusive`，不能猜测通过或失败。
6. 恢复动作遵守确认、幂等、快照与权限边界。
7. Web 明确展示“观察—决定—执行—证据—结果”，不依赖聊天 Markdown 解析。

### 2.2 P1 目标

- 支持把一次有价值的失败建议保存为 Case/Sample 草稿；
- 支持决策质量与 Worker 调用收益指标；
- 支持按 Decision、Plan、Run、CaseRun 交叉检索完整链路；
- 支持比赛演示预置的差异化场景，不写死演示结论。

### 2.3 明确非目标

V2.1 不做：

- 通用 DAG/BPMN 编排器；
- 用户可自由拖拽的“Agent 工作流”；
- 让 Manager 直接调度任意 Worker 或任意 MCP；
- 自动修改或发布 TestCase、Sample、Target、Profile；
- 自动扩大范围、自动开启真实工具、自动发起新的 Run；
- 自动修复被测 Agent 代码；
- 让 Curator 看断言或让 Judge 生成工具结果；
- 保存或展示模型 chain-of-thought；
- 用 LLM 覆盖确定性的 schema、权限、幂等和状态机校验。

### 2.4 成功标准

满足以下条件才算实现：

- 用户可在一个窗口中完成目标描述、计划审核、确认、执行、诊断和恢复建议；
- 决策卡片中的引用可打开真实 Plan、Run、CaseRun、Event、Evaluation 或 Invocation；
- 三个标准场景能证明 Curator/Judge 的调用是动态的；
- 刷新浏览器或 AgentTeams 临时会话丢失后，决策链仍能从 AgentRig 数据库恢复；
- 任何无授权的新 Run、范围扩大、真实工具调用都被 Core 拒绝；
- 默认自动化测试不依赖真实模型、AgentTeams 或外部云服务。

## 3. 核心概念

### 3.1 DecisionRecord

`DecisionRecord` 是 Manager 或 Core 在某个事实快照上做出的、面向业务动作的不可变决策记录。

它记录的是可公开的决策摘要，不是模型内部推理过程。其最小语义是：

```text
在什么触发条件下
+ 看到了哪些已脱敏事实
+ 引用了哪些权威证据
+ 有哪些允许被展示的候选选项
+ 选择了什么动作
+ Core 策略如何裁定
+ 动作最终产生了什么业务结果
```

### 3.2 Observation

一次决策可使用的最小、脱敏、可重建上下文，包括：

- 用户当前目标和显式约束；
- 当前活动 Plan 及修订号；
- 被选 Case、Target、Profile、Sample 的版本或哈希；
- Run/CaseRun 状态摘要；
- 与问题相关的 Event/Evaluation/Invocation；
- AgentTeams 与 Target 健康状态；
- 当前权限与确认状态。

Observation 不复制整个数据库，也不把明文 Secret、全量日志或无关历史发送给模型。

### 3.3 EvidenceRef

`EvidenceRef` 是 DecisionRecord 中指向权威事实的结构化引用：

```json
{
  "kind": "evaluation",
  "resource_id": "eval_123",
  "version": null,
  "snapshot_hash": "sha256:...",
  "label": "Judge 对 case_run_123 的语义评判"
}
```

允许的 `kind` 为：

- `test_case`、`target`、`execution_profile`、`tool_sample`；
- `assistant_event`、`evaluation_plan`、`run`、`case_run`；
- `run_event`、`evaluation`、`agent_invocation`；
- `target_check`、`runtime_health`。

每种引用必须由服务端检查存在性、会话/工作区归属与可见权限。

### 3.4 PolicyVerdict

模型只能提出动作，不能给自己授权。`DecisionPolicyService` 对动作返回：

- `allow`：可立即执行；
- `require_confirmation`：必须绑定真实用户事件；
- `deny`：当前身份或产品策略禁止；
- `stale`：事实快照已变化，必须重新观察和决策。

### 3.5 决策链

同一 Session 中的 DecisionRecord 通过 `parent_decision_id` 组成链：

```text
范围选择
  → 执行策略
  → 提交决策
  → 终态诊断
  → 恢复建议
  → 新 Plan 修订（若用户确认）
```

决策不是原地改写。事实或结论变化时创建新 DecisionRecord，并把旧记录标为 `superseded`。

### 3.6 “动态委派”的准确含义

Manager 负责语义上的委派意图，Core 负责确定性的实际调度：

- Manager 选择计划中的 Provider 策略和 primary evaluator；
- Planner 将选择冻结进 Plan/CaseRun 快照；
- Provider Chain 只有在 fixture/sample 未命中时才真正创建 Curator Invocation；
- CaseExecutor 只有在 primary evaluator 为 `evidence_judge` 时才创建 Judge Invocation；
- AgentTeams 承载两个 Worker 的真实身份、通信和执行生命周期。

因此，Manager 不获得“随意给 Worker 发任务”的通用调度接口。UI 展示的是：

```text
Manager 决策意图 → 冻结执行策略 → Core 运行时分支 → 实际 AgentInvocation
```

这既能证明 AgentTeams 协作是真实的，也不会破坏 V1 的安全边界。

## 4. 总体架构

### 4.1 分层

```text
┌──────────────────────────────────────────────────────────────┐
│ AgentRig Web                                                 │
│ 对话时间线 / 决策卡 / 计划审核 / 动态拓扑 / 证据抽屉        │
└──────────────────────────────┬───────────────────────────────┘
                               │ HTTP + SSE
┌──────────────────────────────▼───────────────────────────────┐
│ AgentRig V2 Application                                     │
│ AssistantService / DecisionService / DecisionPolicyService  │
│ EvaluationPlanService / AgentInvocationService              │
└───────────────┬───────────────────────────┬──────────────────┘
                │                           │
                │ Matrix Bridge + MCP       │ Domain Service
┌───────────────▼────────────────┐  ┌───────▼──────────────────┐
│ AgentTeams                    │  │ AgentRig V1 Core          │
│ Manager                       │  │ Planner / Scheduler       │
│ Simulation Curator Worker     │  │ Provider Chain / Executor │
│ Evidence Judge Worker         │  │ Event / Evaluation        │
└───────────────────────────────┘  └───────────┬───────────────┘
                                               │ Driver / MCP
                                   ┌───────────▼───────────────┐
                                   │ Target：lassist           │
                                   └───────────────────────────┘
```

### 4.2 事实归属

| 事实 | 权威来源 | 说明 |
|---|---|---|
| 用户消息、产品时间线 | AgentRig | `assistant_events` 追加写 |
| 决策及策略裁定 | AgentRig | `decision_records` |
| 计划和修订 | AgentRig | 复用 `evaluation_plans` |
| Run、CaseRun、Evidence、Evaluation | AgentRig V1 | 不复制 |
| Worker 调用投影 | AgentRig | `agent_invocations` |
| Agent 身份与协作通信 | AgentTeams/Matrix | 不作为评测结论 |
| 短期模型上下文 | AgentTeams Runtime | 可丢弃、可重建 |
| Secret | 环境变量或 Secret Manager | 决策和事件只存 `env:` 引用 |

### 4.3 职责边界

| 组件 | 可以做 | 不可以做 |
|---|---|---|
| Manager | 理解目标、查询事实、提出决策、创建计划、解释结果 | 直接 `run_cases`、伪造确认、改变证据 |
| DecisionService | 保存决策、校验引用、状态迁移、绑定结果 | 替代 Manager 做语义判断 |
| PolicyService | allow/confirm/deny/stale、确认绑定、幂等校验 | 生成业务结论 |
| Planner/Core | 展开范围、冻结快照、执行 Provider/Evaluator 分支 | 根据自然语言猜测目标 |
| Curator | 在受限上下文生成候选工具结果 | 看 rubric/断言/最终 verdict |
| Judge | 基于冻结要求和证据独立裁决 | 生成工具结果、修改 Run |
| Web | 展示事实、收集用户确认、发起受限动作 | 从聊天文本推断真实状态 |

### 4.4 自适应循环时序

```text
用户        Web/API       AgentTeams Manager      Decision/Core       V1/Worker
 │             │                  │                     │                  │
 │─目标───────>│─Matrix turn─────>│                     │                  │
 │             │                  │─读取受限上下文─────>│                  │
 │             │                  │<─事实+引用+哈希─────│                  │
 │             │                  │─记录结构化决策─────>│                  │
 │             │                  │<─策略裁定───────────│                  │
 │             │                  │─调用受限领域动作───>│─Plan/Run───────>│
 │             │                  │                     │<─结果/Invocation│
 │             │<────SSE 决策与状态事件────────────────│                  │
 │<─解释/确认──│                  │                     │                  │
 │─确认───────>│─真实事件────────>│─带 event_id 执行────>│                  │
```

### 4.5 与普通工作流的区别

| 固定工作流 | AgentRig 自适应闭环 |
|---|---|
| 预先规定每一步和每个 Worker | Core 规定合法动作，Manager 基于事实选择下一动作 |
| 每次都调用所有节点 | 可以有依据地绕过 Curator/Judge |
| 节点成功即流程成功 | 执行状态与评测结论相互独立 |
| 失败后按固定次数重跑 | 先分类失败，再决定停止、纠正输出、修订计划或询问用户 |
| 流程日志主要证明“走过” | EvidenceRef 证明“为什么走、产生了什么” |

## 5. 决策类型与动态分支

### 5.1 决策类型

`DecisionKind` 第一版固定为：

| 值 | 含义 | 典型输出 |
|---|---|---|
| `clarification` | 缺少会改变结果的关键信息 | 向用户追问或停止 |
| `scope_selection` | 选择 Case、Target、版本与重复次数 | 新建/修订 Plan |
| `execution_strategy` | 选择 Profile、Provider 与 evaluator | 新建/修订 Plan |
| `submission` | 判断是否可确认、提交或取消 | Plan/Run 动作 |
| `diagnosis` | 对终态或异常证据做分类 | 证据化说明 |
| `recovery` | 对可恢复问题提出下一步 | 重试同一调用或新 Plan 修订 |
| `asset_draft` | 将已证明的问题沉淀为草稿 | Case/Sample/Target 草稿 |

### 5.2 触发类型

`DecisionTrigger` 固定为：

- `user_request`：用户提出目标或问题；
- `user_confirmation`：用户确认当前精确版本；
- `plan_validation`：预览发现范围、跳过项或资产漂移；
- `run_progress`：用户明确要求中途诊断；
- `run_terminal`：Run 到达终态；
- `invocation_failed`：Worker 传输、超时或输出校验失败；
- `evidence_inconclusive`：证据不足，无法形成可靠结论；
- `asset_changed`：Plan 后资产版本发生变化；
- `operator_request`：用户明确要求取消、重试或保存草稿。

第一版不由定时器自动发起新的业务决策。Run 终态只投递通知，Manager 在通知回合或用户回合中诊断。

### 5.3 合法动作

`DecisionActionType` 使用白名单，不接受任意工具名：

| 动作 | 结果 | 默认策略 |
|---|---|---|
| `ask_user` | 一条聚焦问题 | allow |
| `no_action` | 停止并说明原因 | allow |
| `create_plan` | 一个 draft Plan | allow |
| `create_plan_revision` | 基于父 Plan 的新 draft | allow；扩大范围时需确认后才可提交 |
| `update_draft_plan` | 更新当前 draft 并重新预览 | allow |
| `request_plan_confirmation` | 展示精确预览 | allow |
| `confirm_plan` | 绑定真实用户消息 | require_confirmation |
| `submit_plan` | 产生唯一 Run | require_confirmation，且 Plan 必须 confirmed |
| `cancel_plan` | 取消未提交 Plan | 用户请求时 allow |
| `cancel_run` | 请求停止已提交 Run | require_confirmation |
| `retry_invocation_delivery` | 同一幂等任务的有限传输重试 | allow，受次数限制 |
| `request_worker_correction` | 对无效结构化结果做一次纠正 | allow，生成新 attempt |
| `create_case_draft` | 保存用例草稿 | 用户明确要求时 allow |
| `create_sample_draft` | 保存样本草稿 | 用户明确要求时 allow |
| `create_target_draft` | 保存 Target 草稿 | 用户明确要求时 allow |

明确没有 `dispatch_arbitrary_agent`、`approve_asset`、`publish_asset`、`override_verdict`、
`run_shell` 或 `run_cases` 动作。

### 5.4 计划阶段分支矩阵

| 观察事实 | Manager 应选择 | Core 行为 |
|---|---|---|
| 目标、Target、Case 均明确 | 创建 draft Plan | 展开预览，不创建 Run |
| 缺少 Target 或版本且会改变结果 | `ask_user` 或建议配置 Target | 不创建 Plan/Run |
| Target 不可达 | 说明健康检查证据 | 不提交 Run |
| 用户指定精确 Case ID | 使用 `case_ids` | 不擅自扩大范围 |
| 用户描述能力范围 | 使用 selector 并展示解析结果 | 标记确认原因 |
| 存在稳定 fixture/sample | Provider Chain 优先 fixture/sample | 运行时可能绕过 Curator |
| 已知存在动态工具结果缺口 | 在 Plan 中允许 Curator fallback | 仅真正缺失时创建 Invocation |
| 断言足以确定结果 | primary evaluator 为 rule | 不创建 Judge Invocation |
| 需要语义 rubric | primary evaluator 为 evidence_judge | 终态证据生成后调用 Judge |
| 两个 Target/版本比较 | A/B Plan | 必须确认，按 pair 比较 |

Manager 可以通过 Plan 的 `selection.overrides.provider_chain` 与
`selection.overrides.primary_evaluator` 表达本次策略，不修改共享 ExecutionProfile。

### 5.5 运行时委派矩阵

#### Simulation Curator

```text
Target 发出工具调用
  → fixture 命中且验证通过：返回，不调用 Curator
  → fixture 未命中，sample 命中且验证通过：返回，不调用 Curator
  → 前序 Provider 均未产出，且策略允许 simulation_curator：创建 Invocation
  → Curator 输出通过 schema/大小/安全校验：固化 Provider Event
  → 输出无效：最多一次 correction attempt
  → 仍无效或超时：Provider exhausted，CaseRun 不伪造结果
```

#### Evidence Judge

```text
CaseRun 执行结束
  → primary evaluator = rule：规则求值，不调用 Judge
  → primary evaluator = external_controller：等待外部结论，不调用 Judge
  → primary evaluator = evidence_judge：创建只读 Invocation
  → 引用有效且输出合法：保存独立 Evaluation
  → 引用不存在/越权：拒绝输出并允许一次 correction
  → 证据不足：保存 inconclusive，不改写为 failed
```

### 5.6 诊断和恢复矩阵

| 问题类型 | 证据 | 允许的恢复 | 禁止行为 |
|---|---|---|---|
| Matrix/HTTP 暂时失败 | delivery 状态、错误码 | 同一幂等消息有限重试 | 创建新 Run |
| Worker 返回非法 JSON | result hash、校验错误 | 一次 correction attempt | 接受部分非法输出 |
| Worker 超时 | deadline、attempt | 停止或由用户要求后重试 | 无限重试 |
| Target 不可达 | target check、driver event | 建议检查配置/稍后新 Plan | 自动换 Target |
| Provider exhausted | provider attempts | 建议补 Sample 或允许 Curator | 伪造工具结果 |
| Rule 断言失败 | assertion、event IDs | 报告产品行为或保存 Case draft | 改成 pass |
| Judge inconclusive | missing evidence refs | 建议补证据或收窄目标 | 猜测 verdict |
| Plan stale | 新旧 selection hash | 创建父子 Plan 修订 | 提交旧 Plan |
| 大量环境型失败 | 分类后的 CaseRuns | 建议有界重跑 | 自动重跑全部 |

### 5.7 三个必须演示的差异化场景

#### 场景 A：资产充分，最短路径

- 同一目标已有 approved Case 和可信 Sample；
- Profile 为 `fixture → sample → simulation_curator`；
- Case 使用规则断言；
- 预期：Curator 调用数为 0，Judge 调用数为 0；
- 价值：证明平台知道什么时候不需要 LLM，成本更低且结果更稳定。

#### 场景 B：动态工具结果与语义评判

- Case 要求的工具调用无 fixture/sample；
- Plan 明确允许 `simulation_curator`；
- Case 有语义 rubric，primary evaluator 为 `evidence_judge`；
- 预期：Curator 和 Judge 各产生真实 Invocation，所有结果带 evidence refs；
- 价值：证明三 Agent 分工是真实业务协作，而非页面角色展示。

#### 场景 C：证据不足后的安全恢复

- Judge 因缺少关键事件返回 `inconclusive`，或 Target 在中途不可达；
- Manager 创建诊断和恢复 DecisionRecord；
- 预期：系统只提出补证据/修订 Plan，不自动把结果判失败，也不自动新建 Run；
- 用户确认新修订后才产生新 Run；
- 价值：证明 Agent 有判断力，同时受安全边界控制。

## 6. DecisionRecord 领域设计

### 6.1 枚举

```python
class DecisionStatus(StrEnum):
    PROPOSED = "proposed"
    AWAITING_CONFIRMATION = "awaiting_confirmation"
    AUTHORIZED = "authorized"
    EXECUTING = "executing"
    SUCCEEDED = "succeeded"
    FAILED = "failed"
    DENIED = "denied"
    STALE = "stale"
    SUPERSEDED = "superseded"
    CANCELLED = "cancelled"

class PolicyVerdictType(StrEnum):
    ALLOW = "allow"
    REQUIRE_CONFIRMATION = "require_confirmation"
    DENY = "deny"
    STALE = "stale"
```

### 6.2 状态机

```text
proposed
  ├─ allow ───────────────→ authorized → executing → succeeded
  │                                      └─────────→ failed
  ├─ require_confirmation → awaiting_confirmation
  │                           ├─ valid user event → authorized
  │                           ├─ facts changed ───→ stale
  │                           └─ user rejects ────→ cancelled
  ├─ deny ─────────────────→ denied
  └─ newer decision ───────→ superseded
```

终态不可回退。失败重试创建子 DecisionRecord 或新的 Invocation attempt，不复写原始决定。

### 6.3 决策提案协议

Manager 通过 `record_manager_decision` 提交严格结构化对象：

```json
{
  "schema_version": "agentrig.manager-decision.v1",
  "session_id": "session_123",
  "turn_id": "turn_123",
  "parent_decision_id": null,
  "trigger": "user_request",
  "decision_kind": "execution_strategy",
  "objective": "验证 lassist 当前版本的项目打开能力",
  "observation_summary": {
    "known": ["Target 健康检查通过", "已解析 4 个 approved cases"],
    "unknown": [],
    "constraints": ["不调用真实外部工具"]
  },
  "options": [
    {
      "action_type": "create_plan",
      "label": "优先复用样本，缺失时委派 Curator",
      "expected_effect": "减少模型调用且覆盖动态缺口"
    },
    {
      "action_type": "ask_user",
      "label": "要求用户补充全部工具结果",
      "expected_effect": "延后执行"
    }
  ],
  "selected_action": {
    "action_type": "create_plan",
    "parameters": {
      "provider_chain": ["fixture", "sample", "simulation_curator"],
      "primary_evaluator": "evidence_judge"
    }
  },
  "rationale_summary": {
    "summary": "现有样本覆盖稳定分支，动态缺口需要受限生成；语义要求无法由规则完全表达。",
    "tradeoffs": ["可能增加两次 Worker 模型调用"]
  },
  "evidence_refs": [
    {"kind": "target_check", "resource_id": "check_123"},
    {"kind": "test_case", "resource_id": "case_open_project"},
    {"kind": "execution_profile", "resource_id": "profile_managed"}
  ],
  "confidence": 0.86
}
```

服务端忽略模型提交的任何 `authorized=true` 或自定义权限字段。是否需确认完全由 PolicyService 重算。

### 6.4 字段规则

- `objective`：最多 500 字，不得包含 Secret；
- `known/unknown/constraints`：各最多 20 项，每项最多 500 字；
- `options`：1—5 项，只允许白名单动作；
- `selected_action`：必须是 options 中的一项；
- `rationale_summary`：用户可见的简要理由，不要求也不接受逐 token 思维过程；
- `evidence_refs`：至少一项，纯澄清问题可引用用户消息；
- `confidence`：0—1，仅供提示，不参与自动授权；
- `parameters`：按 action type 使用 discriminated union schema；
- 所有自由文本经过敏感信息检测和长度限制。

### 6.5 不可变性

以下字段创建后不可修改：

- trigger、decision_kind；
- observation_summary、options、selected_action；
- rationale_summary、evidence_refs、context_hash；
- proposed_by、session_id、turn_id、parent_decision_id。

只允许状态机服务更新：status、policy_verdict、确认信息、action ref、错误和时间戳。

### 6.6 上下文哈希

`context_hash` 由以下规范化内容计算 SHA-256：

```text
session_id + turn_id + active_plan_id/revision
+ sorted(evidence_ref.kind, resource_id, version, snapshot_hash)
+ selected_action canonical JSON
```

执行有副作用动作前重新解析引用并计算哈希。变化则返回 `stale`，Manager 必须创建新决策；不允许只
刷新旧记录的哈希。

### 6.7 幂等

- 决策提案唯一键：`(session_id, turn_id, ordinal)`；
- 同一个 AgentTeams tool call 重试返回原 DecisionRecord；
- 每个可执行决策有一个 `action_idempotency_key`；
- Plan submit 继续复用现有 `submit_idempotency_key`；
- Worker 重试沿用逻辑任务 key 并增加 attempt，保留每个 Invocation；
- 已 `succeeded` 的决策再次执行只返回原 action ref。

### 8.2 DecisionContextBuilder

输入：

```python
build(
    session_id: str,
    turn_id: str,
    focus: Literal["planning", "submission", "diagnosis", "recovery"],
    run_id: str | None = None,
    case_run_ids: list[str] | None = None,

```

输出按 focus 限制：

- `planning`：当前目标、活动 Plan、Case/Target/Profile 摘要、target check；
- `submission`：Plan 精确 revision、preview、selection hash、确认原因；

### 8.3 DecisionPolicyService

核心接口：

```python
class DecisionPolicyService:
    async def evaluate(
        self,
        proposal: ManagerDecisionProposal,
        resolved_context: DecisionContext,
    ) -> PolicyVerdict: ...

    async def authorize(
        self,
        decision_id: str,
        confirmation_event_id: str | None,
    ) -> DecisionRecordView: ...
```

规则必须是代码和配置，不是 Prompt。首版规则：

| 条件 | 裁定 |
|---|---|
| 只读诊断、ask_user、no_action | allow |
| 创建/更新 draft 且未扩大用户明确范围 | allow |
| selector、A/B、repeat > 1、real_tool、planned > 20 | require_confirmation |
| confirm/submit/cancel run | require_confirmation |
| 真实用户事件不属于当前 Session | deny |
| confirmation 早于当前 Plan revision | stale |
| 引用不存在、跨工作区或已变化 | stale/deny |
| Manager 请求 raw run_cases、发布资产、改 allowlist | deny |
| 自动创建新 Run 作为恢复 | deny |
| 同一 delivery 有剩余 retry budget | allow |
| correction attempt 已达到上限 | deny |

`policy_verdict.rule_version` 首版为 `agentrig.decision-policy.v1`，便于后续解释规则变化。

### 8.4 DecisionService

职责：

1. 解析和校验 Decision proposal；
2. 解析 EvidenceRef 并计算 context hash；
3. 调用 PolicyService；
4. 原子保存 DecisionRecord 和 `decision_recorded` event；
5. 授权时校验真实 user event；
6. 用 compare-and-set 执行状态迁移；
7. 为动作签发一次性 `DecisionAuthorization`；
8. 绑定 action ref 并写终态事件；
9. 对重复请求返回同一结果；
10. 不直接实现 Plan/Run/Asset 业务逻辑。

### 8.5 动作执行方式

不提供一个能执行任意字符串的 `execute_decision(action_name, payload)`。Manager 仍调用领域专用工具：

```text
record_manager_decision(...)
  → decision_id + policy verdict

create_evaluation_plan(..., decision_id)
update_evaluation_plan(..., decision_id)
confirm_evaluation_plan(..., decision_id, confirmation_event_id)
submit_evaluation_plan(..., decision_id)
cancel_run(..., decision_id)
```

每个有副作用的 Service 在事务边界内：

1. claim 对应 decision；
2. 验证 action type 和参数摘要匹配；
3. 将 decision 置为 executing；
4. 执行已有领域服务；
5. 绑定结果并置为 succeeded；
6. 失败时保存错误并置为 failed。

这样可以避免 Agent 先记录“安全动作”，再用同一个 decision ID 调用另一个危险动作。

### 8.6 与 EvaluationPlan 的关系

- 不新建 `PlanRevision` 表；现有 `parent_plan_id + revision` 已满足修订；
- `create_plan_revision` 必须传父 Plan，复制目标后再应用显式差异；
- 已 confirmed/submitted/cancelled 的 Plan 不可更新；
- 新 Plan 保存 `origin_decision_id`；
- Plan `reasoning_summary` 只保留与该计划直接相关的摘要，完整选项和策略裁定读取 DecisionRecord；
- submit 前仍调用 `preview_run_cases` 并比对 selection hash；
- Decision 授权不能绕过 Plan 自己的状态机。

### 8.7 与 AgentInvocation 的关系

- Curator/Judge 的 invocation 状态机保持不变；
- `AgentRole` 仍只有 `simulation_curator` 和 `evidence_judge`；
- Manager 是会话主 Agent，不伪装成 Worker invocation；
- Worker input_snapshot 继续按角色最小化并脱敏；
- runtime 根据冻结 Profile 创建 Invocation，不能由浏览器伪造；
- correction 生成新 attempt 和新 invocation id，旧失败记录保留；
- UI 通过 Plan/Run/CaseRun 和可选 origin decision 连接两类事实。

### 8.8 事务与并发

- 创建决策和追加 `decision_recorded` event 在同一数据库事务；
- 使用 `(session_id, turn_id, ordinal)` 防止 Matrix 重投重复创建；
- action claim 使用条件更新 `authorized → executing`；
- 两个实例同时提交时只有一个获得 claim；
- Plan submit 继续使用现有 application lock 与 idempotency key；
- SSE 只投影已提交事务；
- Run/Worker 长任务不持有数据库事务，先保存状态再异步执行。

### 8.9 服务重启恢复

启动时除现有 Run/TargetChat/Invocation interrupted 处理外，增加：

- `proposed/awaiting_confirmation`：保持原状态；
- `authorized`：可由同一动作请求继续，系统不主动执行；
- `executing` 且已有 action ref：核对目标资源并补齐 succeeded；
- `executing` 且无 action ref：标记 failed/interrupted；
- 不在启动时自动提交 Plan 或创建 Run；
- 恢复结果写 `system_notice` 和 decision status event。

执行约束：

1. 先恢复 session/turn；
2. 只为会改变业务状态、选择路径或形成诊断结论的动作记录决策；
3. 普通分页读取不逐条创建决策，避免审计噪音；
4. 记录决策后只能调用与 `selected_action` 匹配的专用工具；
5. 如果 policy 要求确认，向用户展示精确影响并停止当前执行；
6. 收到确认后重新读取上下文，不能复用过期事实；
7. 最终答复引用 decision/plan/run ID，不输出隐藏 reasoning。

### 9.4 AgentTeams 身份不变

不增加第四个“Orchestrator Agent”。三角色保持：

- Manager：自适应语义大脑；
- Curator：工具结果专业 Worker；
- Judge：证据裁决专业 Worker。

自适应控制器是 AgentRig 的确定性应用服务，不是第四个模型 Agent，也不计入比赛 Agent 身份。

### 9.5 Prompt injection 防护

- Case、Target output、tool result、Matrix 历史均标注为 untrusted evidence；
- Manager 只能看到 MCP 返回的动作白名单；
- Worker 无 Manager MCP token；
- Curator 看不到 rubric/assertions/Judge 结果；
- Judge 只能引用输入快照中的 evidence IDs；
- 任何证据文本中的“请调用工具/忽略规则”都只作为数据；
- DecisionService 不信任模型声明的身份、权限、确认或资源归属。

## 10. HTTP 与 SSE 设计

### 10.1 查询 API

```http
GET /api/v2/assistant/sessions/{session_id}/decisions
GET /api/v2/decisions/{decision_id}
```

列表参数：

```text
after_id?
status?
decision_kind?
limit=50
```

响应使用稳定 Page schema，按 `created_at, id` 排序。详情响应可以包含解析后的 `links`，但不内嵌完整
Run/Event 数据。

### 10.2 用户动作 API

```http
POST /api/v2/decisions/{decision_id}/confirm
POST /api/v2/decisions/{decision_id}/cancel
```

确认请求：

```json
{
  "confirmation_event_id": "event_user_123"
}
```

该接口只授权 Decision。若动作是 Plan confirm/submit，Manager 或 Web 随后仍通过对应领域 API 执行，
领域状态机再次验证 decision。首版 UI 推荐继续让“确认计划”按钮调用 Plan confirm，并在服务内部完成
Decision 授权，避免用户操作两次。

不提供面向浏览器的通用 `execute` API。

### 10.3 现有 API 兼容扩展

以下请求体增加可选 `decision_id`：

- Plan create/patch/confirm/submit/cancel；
- Run cancel；
- Managed draft asset create/update。

响应增加 `origin_decision_id`，旧客户端忽略即可。

### 10.4 SSE

继续复用：

```http
GET /api/v2/assistant/sessions/{id}/stream?after_seq=N
```

客户端看到 `decision_recorded` 或 `decision_status_changed` 时：

- 更新 Session timeline；
- invalidate 当前 decision 查询；
- 若 payload 含 plan/run/invocation ref，再更新对应查询；
- 断线后仍按 `after_seq` 续传，不直接订阅 Matrix。

### 10.5 错误契约

建议新增错误码：

| code | HTTP | 含义 |
|---|---:|---|
| `decision_invalid` | 422 | schema、选项或引用不合法 |
| `decision_denied` | 403 | 策略拒绝动作 |
| `decision_confirmation_required` | 409 | 缺少真实用户确认 |
| `decision_stale` | 409 | 上下文或引用变化 |
| `decision_action_mismatch` | 409 | decision 与领域工具不匹配 |
| `decision_already_claimed` | 409 | 另一个执行者正在执行 |
| `decision_retry_exhausted` | 409 | 超过有限恢复预算 |

错误 `details` 只返回用户可操作信息和资源 ID，不返回 prompt、token、Secret 或内部堆栈。

## 11. 前端产品与交互设计

### 11.1 设计原则

1. 用户首先看到“当前目标和下一步”，其次才是底层 Agent 协作。
2. 界面只展示后端结构化事实，不从助手文本猜 Plan、Run 或 Agent 状态。
3. “未调用 Worker”是有效结果，要明确解释为策略绕过，而不是显示成缺失。
4. 中文是产品主语言；协议名、ID、枚举和技术实体保留英文，避免中英文重复标题。
5. 动效只表达真实状态迁移，不模拟虚假的 Agent 思考过程。
6. 默认信息密度适合演示；详细 JSON、输入快照和哈希放在抽屉内。

### 11.2 智能评测助手布局

沿用现有三栏，不重构整个平台导航：

```text
┌──────────────┬────────────────────────────────┬──────────────────────┐
│ 评测会话      │ 对话与决策时间线                 │ 当前评测控制室         │
│              │                                │                      │
│ 搜索/筛选     │ 用户消息                        │ 当前目标               │
│ Session 列表 │ Manager 回复                    │ 当前决策               │
│ 状态/时间     │ Decision Card                  │ EvaluationPlan         │
│              │ Run/Worker Activity            │ 动态协作拓扑           │
│              │ 确认条                          │ Evidence 摘要           │
└──────────────┴────────────────────────────────┴──────────────────────┘
```

桌面宽度建议：左栏 264px、中央 `minmax(520px, 1fr)`、右栏 380px。小于 1180px 时右栏改为抽屉；
小于 760px 时左栏改为会话选择器。

### 11.3 Decision Card

每条关键决策使用统一卡片：

```text
┌─ 执行策略 · 已执行 ───────────────────────────────┐
│ 决定：优先使用已有样本，缺失时委派 Curator         │
│                                                   │
│ 依据  4 个已批准用例 · Target 健康 · 样本覆盖 3/4 │
│ 影响  最多 1 次 Curator 调用 · 使用语义 Judge      │
│ 策略  需要确认：语义 selector                      │
│                                                   │
│ [查看依据] [打开计划 plan_…]                       │
└───────────────────────────────────────────────────┘
```

卡片字段：

- 类型与状态；
- 一句话 selected action；
- 2—4 条 observation 摘要；
- 影响/成本/风险；
- Policy verdict 与确认原因；
- action ref；
- Evidence 抽屉入口。

默认不展示完整 options。展开后展示“已选方案”和最多四个“未选方案及简短取舍”，不展示内部思维链。

### 11.4 动态协作拓扑

右栏拓扑根据真实数据渲染：

```text
Manager
  │ Decision: execution_strategy
  ▼
AgentRig Core ───────────────→ Target: lassist
  │
  ├─ Curator   已绕过 / 运行中 / 成功 / 失败
  └─ Judge     已绕过 / 运行中 / 成功 / 不确定
```

状态来源：

| UI 状态 | 计算依据 |
|---|---|
| `等待决策` | 无 execution strategy decision |
| `计划允许` | provider/evaluator 在 Plan snapshot 中 |
| `已绕过` | Run 已经过对应阶段且无 Invocation，确定性路径已产出 |
| `待调用` | Plan 允许但运行尚未到达分支 |
| `运行中` | Invocation dispatched/running |
| `成功` | Invocation completed 且结果被 Core 接受 |
| `失败` | Invocation failed/timed_out |
| `不确定` | Judge Evaluation outcome=inconclusive |

不能仅因为 Profile 包含 Curator 就显示“Curator 已参与”。

### 11.5 Evidence 抽屉

点击 EvidenceRef 打开统一抽屉：

- 顶部：kind、资源 ID、版本/哈希、产生时间；
- 中部：对用户有用的格式化摘要；
- 下部：关联 Decision → Plan → Run → CaseRun → Event/Evaluation/Invocation；
- 技术详情：折叠 JSON，默认脱敏；
- 跳转：打开已有资产/Run/CaseRun 页面。

资源不存在或无权限时显示“引用当前不可访问”，但保留 ID 和决策原始摘要。

### 11.6 确认交互

确认条必须列出：

- Plan ID 和 revision；
- 解析后的 CaseRun 数；
- Target/版本；
- provider chain 和 primary evaluators；
- selector、A/B、repeat、real tool、大批量等风险原因；
- “确认后将创建一个新的 Run”的明确说明。

按钮：

- `确认并运行`；
- `修改计划`；
- `取消`。

用户确认产生真实 `user_message` event，再由后端将该 event ID 绑定 Decision 和 Plan。不能由前端传
`confirmed_by: user` 代替真实事件。

### 11.7 恢复建议卡

恢复卡不使用“一键自动修复”措辞。示例：

```text
证据不足，暂时无法判断

缺少：项目查询工具的有效返回事件
建议：允许 Simulation Curator 补齐该工具结果后，仅重跑 1 个失败用例
影响：将创建 Plan revision 3 和一个新 Run

[查看证据] [生成修订计划] [暂不处理]
```

“生成修订计划”只创建 draft；之后仍走预览与确认。

### 11.8 Run 详情增量

在现有 Run 详情增加：

- `决策链` Tab：按时间展示与 Run 相关的 DecisionRecord；
- CaseRun 行增加 Curator/Judge 调用标识；
- AgentTeams Tab 区分“计划允许”和“实际调用”；
- Evaluation 区分 Rule、Judge、External Controller，不合并 verdict；
- 失败分类链接到诊断 Decision；
- 从恢复 Decision 打开新 Plan revision，并能返回原 Run。

### 11.9 前端文件变更

```text

  + DecisionRecord / EvidenceRef / PolicyVerdict 类型和 API

  + decisions query
```

## 12. 安全、权限与隐私

### 12.1 最小权限

| 身份 | 决策能力 | 领域能力 |
|---|---|---|
| Manager | 提议、查询自己的 Session 决策 | Manager MCP 白名单 |
| Curator | 无 | claim/submit/fail Curator Invocation |
| Judge | 无 | claim/submit/fail Judge Invocation |
| Web user | 查询可见决策、确认/取消 | 当前产品权限内操作 |
| System | 状态恢复、投影事件 | 不生成语义结论 |

### 12.2 确认边界

以下行为第一版始终需要当前用户明确确认：

- 提交任何 Managed Plan；
- A/B、selector、repeat > 1、大于 20 CaseRuns；
- 使用 `real_tool`；
- 扩大 Case/Target 范围；
- 取消已经开始的 Run；
- 以恢复名义创建新的 Run。

创建 draft 不等于授权执行。Manager、Curator、Judge、System 消息都不是用户确认。

### 12.3 Secret 与脱敏

- 配置只保存 `env:VARIABLE_NAME`；
- Decision proposal、error、event 在入库前调用现有 `Redactor`；
- `selected_action.parameters` 使用各动作 schema 的 secret validator；
- Evidence 抽屉不显示 Worker 输入中的 Secret；
- 日志不得输出完整请求体；
- Matrix 消息只发送完成任务所需的最小快照。

### 12.4 审计

每次有副作用的 Managed 动作必须能够回答：

```text
谁提出 → 基于什么 → 策略版本 → 谁确认 → 何时执行
→ 影响哪个资源 → 是否成功 → 失败原因 → 是否发生后续恢复
```

如果任一关键引用缺失，动作不得进入 `succeeded`。

### 14.7 三条核心 E2E

#### E2E-A：最短确定性路径

断言：

- decision action 为 create_plan；
- Plan provider chain 含 sample fallback；
- Run 成功；
- Curator invocations = 0；
- Judge invocations = 0；
- UI 显示两者“已绕过”及原因；
- Rule Evaluation 引用真实 events。

#### E2E-B：三 Agent 真实协作

断言：

- Manager DecisionRecord 存在且引用 Case/Profile/Target；
- Curator Invocation completed，输入看不到 rubric；
- Judge Invocation completed，输入只含有效 evidence refs；
- Decision → Plan → Run → Invocation → Evaluation 可完整导航；
- AgentTeams/Matrix request/response event IDs 可审计。

#### E2E-C：不确定与恢复

断言：

- 初次 Evaluation 为 inconclusive；
- recovery decision 为 awaiting_confirmation 或 succeeded(draft only)；
- 用户确认前 Run 数量不增加；
- 修订 Plan 的 parent_plan_id 正确；
- 确认后只创建一个新 Run；
- 原 Run、原 Decision 和原 Evaluation 未被覆盖。

### 14.8 非功能测试

- 500 条 Session events + 100 条 decisions 的页面加载与 SSE；
- 50 个并发 Session 的 decision ordinal/seq；
- Worker timeout、Matrix 断开、数据库重启；
- 10KB 恶意证据文本、超深 JSON、重复 EvidenceRef；
- Model 返回未知 action、NaN confidence、伪造 authorization；
- AgentTeams 完全关闭时 V1 Core 回归不受影响。

## 17. 风险与取舍

| 风险 | 影响 | 控制方式 |
|---|---|---|
| 决策记录过多 | UI 噪音、存储增长 | 只记录关键业务选择，普通 read 不记录 |
| 模型理由听起来合理但证据弱 | 降低可信度 | 至少一个有效 EvidenceRef，Core 校验引用 |
| Decision 与实际动作不一致 | 审计失真 | action schema 匹配 + claim token + result ref |
| 资产在确认后变化 | 执行范围漂移 | context/selection hash，submit 前重算 |
| 为展示 Agent 而强制调用 Worker | 成本与结论变差 | 显示“已绕过”也作为正向能力 |
| 自动恢复变成隐式重跑 | 成本和安全风险 | 新 Run 始终新 Plan revision + 用户确认 |
| UI 过度展示技术细节 | 用户看不懂 | 摘要优先，ID/JSON 放抽屉 |
| 决策模块演化成工作流引擎 | 偏离产品定位 | 白名单动作、专用领域 API、无 DAG 设计器 |

关键取舍：

1. 选择“一张决策表 + 复用现有领域对象”，不增加 Cycle/Task/Node 等通用编排表。
2. 选择“Manager 提出、Core 执行”，不让 LLM 持有最终授权。
3. 选择“实际需要才调用 Worker”，不把三 Agent 全调用作为每次运行的硬规则。
4. 选择“安全恢复建议”，不在第一版做无人值守自动重跑。
5. 选择“可公开理由摘要”，不记录模型隐藏思维过程。

## 18. 开发完成后的最终用户体验

用户只需要进入 lassist 的“智能评测助手”并输入：

> 检查当前版本项目打开和项目列表查询能力，优先复用已有样本；没有可靠工具结果时再模拟，语义结果
> 需要独立判断。

系统应完成：

1. Manager 查询真实 Case、Target、Profile、Sample 和健康状态；
2. 页面出现一条有证据引用的执行策略 Decision；
3. Manager 生成可编辑 Plan，清楚显示预计 CaseRuns、Provider、Evaluator 和风险；
4. 用户确认精确 revision；
5. V1 Core 创建并执行唯一 Run；
6. 有样本的工具调用绕过 Curator，缺失的调用才进入 AgentTeams Curator；
7. 规则足够的 CaseRun 直接规则评判，语义 CaseRun 才进入 Judge；
8. 页面实时显示真实决策、调用、证据和结果；
9. Manager 基于冻结证据解释结论；
10. 若证据不足，只提出有界恢复方案，用户确认新 Plan revision 后才再次运行。

最终界面展示的不是一条预先画好的 Agent 流程，而是一套能够证明以下价值的评测系统：

> 它知道该测什么、为什么这样测、什么时候需要其他 Agent、什么时候不需要、结论依据在哪里，失败后
> 如何安全地继续。

这就是 AgentRig V2.1 相比普通测试工作流、普通聊天助手和只做 LLM-as-a-Judge 工具的核心差异。
