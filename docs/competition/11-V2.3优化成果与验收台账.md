## 1. 这轮优化把作品从哪里推进到哪里

```text
历史比赛版本
  三 Agent 计划 / 受控工具 / 证据裁决
        │
        ▼
当前版本
  运行环境冻结 → A/B 质量对比 → Release Gate
        │
        ▼
  OTLP 生产 Trace → 人工审核 Case → Judge 对齐 → 失败复发监控
        │
        ▼
  Project 隔离 + PostgreSQL Job/Attempt/lease/fencing + 有界恢复
```

三 Agent 仍然是语义协作层；Capability、Gate、生产证据、人工治理和耐久调度都由确定性 Core
保存权威事实。升级没有把 Prompt 变成权限边界，也没有用新 Runtime 覆盖旧 Live 证据。

## 4. 评委可现场复核的四条链

### 4.1 发布前 A/B 链

```text
Browser 创建 paired Run
  → baseline / candidate CaseRun
  → Capability Snapshot/hash
  → QualityReport + ComparisonReport
  → versioned ReleasePolicy
  → ReleaseGate verdict/checks/policy_hash/result_hash
```

可重复入口：

```bash
scripts/reference_demo.sh all --profile reference-ci
```

已知 `candidate-regression` 必须被 Gate 阻断；三份报告必须具有同一 source snapshot hash。

### 4.2 多 Agent 历史 Live 链

```text
用户确认 → EvaluationPlan revision → Manager submit
  → Matrix request → Curator/Judge role MCP → Matrix response
  → RunEvent / Rule / Judge evidence refs
```

该链使用 AgentTeams `v1.1.2` + lassist 历史证据，见
[真实运行证据报告](./07-真实运行证据报告.md)。`v1.2.2` 必须生成自己的 observation/compat report，
不得通过改版本字段复用旧证据。

### 4.3 生产失败资产化链

```text
OTLP protobuf → Source/Project scope → quota/redaction/idempotency
  → ProductionTrace/Span（不等于 Run）
  → Trace 转 draft Case + lineage
  → Reviewer/Adjudicator → approved Case
  → replay / GoldLabel / Judge Alignment
```

任何自动化都不能跳过 draft/review；原 Trace 和历史 Evaluation 不被修改。

### 4.4 耐久执行与复发链

```text
ExecutionJob → Attempt → SKIP LOCKED claim → lease + fencing token
  → heartbeat / cancel / reaper / late-result reconciliation
  → Run atomic terminal lock → one completion notification
  → Failure Pattern → verified Run → resolved / regressed
```

PostgreSQL 17.7 的双 Worker、并发终态、OTLP retention 和 migration 往返已实测；容量与长时 SLO
仍需目标部署环境证明。

## 7. 最终提交冻结规则

1. 先提交全部优化，得到最终 git SHA；
2. 在干净 checkout 重跑 ReferenceEvidence、全量 CI 与 `--require-clean-source`；
3. 生成 PPTX/PDF、视频/SRT、wheel/sdist、SBOM、当前报告和 SHA-256；
4. 对 Git 历史、源码、解压包、提交目录和 ZIP 做 Gitleaks；
5. 将外部 Live 的 pass/fail/limitation 原样归档；缺失时保留 Pending；
6. 由参赛人确认团队信息、仓库公开、协议接受、上传和最终提交。

当前工作区含尚未提交的优化，因此本轮重建制品是“候选提交包”。它可以完整展示当前实现，但在
参赛人 commit/push 前不能填入最终 git SHA、GitHub CI Run 或 `source_dirty=false`。
