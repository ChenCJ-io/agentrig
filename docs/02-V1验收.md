## AgentScope / Pixcake 真实协议

验收时明确区分了两个服务：

- `http://127.0.0.1:8002/mcp/`：TS Agent Scope 管理平台，只读获取已审核用例；
- `http://127.0.0.1:8000/chat/stream`：实际 Pixcake 被测 Agent。

使用 AgentScope 已审核用例先在原平台跑基线，再通过 AgentRig `controlled` 模式向同一个
Pixcake Agent 回灌 Fixture：

| AgentScope 用例 | 场景 | AgentScope 基线 | AgentRig |
| --- | --- | --- | --- |
| `tc_from_error_099` | 单轮 `apply_image_prompt` | 工具结果回灌闭环完成 | passed |
| `tc_from_error_080` | 跨轮 `apply_image_prompt → rollback_to_tool_call` | passed | passed |
| `tc_from_error_081` | 同轮 `get_project_list → open_project` | passed | passed |

第三条还校验了 `open_project.project_id=430409687` 确实来自前一次工具结果。三条 AgentRig
真实兼容性测试共耗时 34.39 秒，覆盖：

- `user_id`、`device_info`、`chat_channel` 请求字段有效；
- TargetVersion 只覆盖 `device_info.app_version/tool_version` 时，会与 Target 公共配置递归
  合并；
- 每个 HTTP 请求的 `request_id`、请求类型、耗时和 TTFT，以及会话 `session_id`，均进入
  CaseRun 证据；
- `session_created`、真实文本片段、工具调用、完成事件能按发生顺序归一并持久化；
- 不要求被测 Agent 挂载业务 MCP 工具，AgentRig 可以直接向 `/chat/stream` 提供工具结果；
- 同一用户轮内可连续处理多次“工具调用 → Fixture 结果 → 继续推理”；
- 跨用户轮沿用 `session_id` 和 `metadata`，但只在第一条消息发送初始附件；
- 不开启 AgentRig Evidence Judge，不额外混入平台评判；
- 需要项目/附件的用例必须通过 `initial_state.pixcake_request` 明确注入，Core 不猜测业务
  环境。

另通过正式 MCP 入口，以并发 3、不指定版本的方式执行上述三个用例：3 个兼容项全部
pass，3 个不兼容的用例×版本组合返回 `version_incompatible` skipped，批次约 15 秒完成。

另跑了 `tc_from_error_103` 作为负向观察：当前 Agent 对预期纯文本的请求实际调用了
`apply_image_prompt`，AgentScope 也判失败。这属于被测 Agent 行为，不是 Driver 适配问题。

还有一个语义映射边界：部分 AgentScope 用例声明 `expected_first_action=tool_call`，但当前
Pixcake Agent 会先输出“我来处理”一类短文本再调用工具。AgentRig 的 `first_action=tool`
规则按真实事件顺序严格判断，因此真实兼容性测试只验证工具闭环，没有替 AgentScope 放宽
该规则。后续若做用例自动导入，需要明确选择“严格首事件”还是“忽略工具前提示语”。

默认测试不会访问真实模型，以上三条测试会跳过；显式复验：

```bash
AGENTRIG_TEST_PIXCAKE_URL=http://127.0.0.1:8000 \
  uv run pytest -q tests/compat/test_agentscope_pixcake_live.py -vv
```

## Goose / ACP 真实兼容性

使用 Goose `v1.45.0`、官方 Python `agent-client-protocol 0.11.1` 和
`deepseek-v4-flash` 完成 AgentRig 真实纵向测试：

```text
AgentRig CaseRun
→ ACP Driver 启动独立 Goose 容器
→ session/new 注入 CaseRun MCP Proxy
→ Goose 调用工具
→ Fixture / approved Sample 返回结果
→ Goose 继续推理
→ Rule 评判与事件存档
```

同一 Run 以 `concurrency=3` 并发完成三条 CaseRun，实测约 7.2 秒：

- 单轮 `get_weather`：Fixture 命中，工具参数、结果和最终文本全部通过；
- 两轮 `get_project_list → open_project`：第二轮参数 `project_id=430409687`
  来自第一轮工具结果，同一 ACP Session 保持上下文；
- 单轮 `get_exchange_rate`：用例无 Fixture，由 Target `tool_catalog` 提供工具定义，
  Provider 链按 `Fixture miss → approved Sample hit` 返回结果。

同时验证：

- 每个 CaseRun 的 Goose config/data/state/workspace 完全隔离；
- `driver_request started < tool_call < tool_result < driver_request completed`；
- Session、usage、assistant text、Provider attempt、validation 和 Rule 证据完整；
- ACP `session/close` 后按 EOF → TERM → KILL 分级清理；
- 执行结束没有残留容器、进程或 CaseRun 运行目录。

显式复验：

```bash
AGENTRIG_TEST_GOOSE_LIVE=1 \
DEEPSEEK_API_KEY='<provided separately>' \
uv run pytest -q tests/compat/test_goose_acp_live.py -vv
```
